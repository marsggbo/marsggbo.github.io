# Jev 拆解 | 一个不生成 token 的模型，怎么做决策？

> 参考资料：[TypeSafe 官方发布博客](https://typesafe.ai/blog/introducing-system-one-models-and-jev) · [TypeSafe 官方文档](https://docs.typesafe.ai/) · [NanoJev（开源复现）](https://github.com/TianyuCodings/NanoJev)

---

## 1. 为什么一个“只会判断”的模型，反而有这么多地方能用

先看几个场景。

**客服系统**收到一句“信用卡被重复扣款了”，真正要做的不是写一篇分析，而是判断它该去账单、退款还是账户安全队列；**搜索和推荐**拿到几百个候选结果，也不是再生成一份网页，而是判断哪一个应该排在前面；**Agent**准备调用工具时，需要判断的是“这一步是否安全”“该调用哪个 API”“要不要先问用户确认”；放到游戏里，则变成判断下一步往东、西、南、北哪个方向走。

这些任务表面上差很多，底层其实是同一件事：

> **给定当前状态和一组候选，判断每个候选有多大可能是对的。**

分类并不新，为什么这件事现在又变得重要了？因为 LLM 进入 Agent 和 workflow 之后，很多任务已经不是“帮我写一段话”，而是“下一步到底做什么”。这类判断会出现在一条 workflow 的每个节点上：先判断请求属于哪一类，再判断该调哪个工具，执行后还要判断结果是否可信。单次分类看起来不起眼，但一天跑几百万次以后，生成式 LLM 的解码延迟、输出成本和格式错误就都放大了。

传统做法通常是把候选写进 prompt，让 LLM 最后回答 `A/B/C` 或一段 JSON。问题是答案明明只有一个选项，模型仍然要一个 token 一个 token 地生成；生成后还要检查 JSON 是否合法、选项是否越界，而且 next-token 概率也不天然等于“这个判断有多可信”。

TypeSafe AI 今年 9 月发布的 **Jev**，就是冲着这个问题来的。它不生成文本，只接收一段 `state`（当前状态）和若干个 `question`（要做的判断），直接返回完整概率分布。例如：

```text
state: 用户说“信用卡被重复扣款了”
question: 应该路由到哪个队列？

billing       0.91
refund        0.06
account       0.02
security      0.01
```

概率分布比单独返回一个 `billing` 更有用：0.91 时可以直接执行；如果前两项分别是 0.43 和 0.41，系统就知道这次判断并不稳，可以追问用户或转人工。**Jev 真正卖的不是“会分类”，而是把自然语言理解变成一个能直接驱动下一步动作的概率接口。**

官方展示的应用基本都沿着这条线展开：

- **智能家居**：一次判断请求类型、房间、设备和动作，直接控制后续执行；
- **Wikiracing / 检索重排**：面对一个页面里的几百个链接，判断下一跳选哪个；
- **实时游戏 AI**：根据当前局面判断移动方向或是否开枪；
- **Agent trace 和安全事件判断**：决定一步操作是否异常、是否应该拦截；
- **发票抽取、客服路由**：把自由文本映射成有限字段或业务队列。

官方博文给出的数字是自家工作流里 **20–200× 更快、40–400× 更便宜**。这类数字当然要结合输入长度、网络位置和对比方法看，不能直接当通用 benchmark；但方向很好理解：**如果任务最终只需要做决定，就没必要为“生成一段答案”付完整的解码成本。**

下图是 NanoJev 仓库里的对比演示：Jev、NanoJev 和未经微调的 Qwen3-0.6B 同时走迷宫。这里模型每一步做的事情都很简单——给几个可行方向分配概率——但这些连续的小判断最终决定了能不能走到出口。

![Jev vs NanoJev vs 未微调 Qwen 迷宫探索对比](/assets/img/posts/20260919-jev/000_side_by_side_maze.png)

理解了“分类其实是 workflow 的控制面”之后，再看它为什么要设计 Choice、Score 和 Boolean 三种接口，以及一个模型怎么应付每次都不同的候选集合，就顺了。

## 2. Jev 把判断拆成了三种接口

一次请求由两部分组成：`state`（字符串/JSON/数组，多个问题可共用）和 `questions`（每个问题有自己的 `type`、`instructions`、`criteria`）。**问题之间互相独立，不能读取彼此答案**，这是接口层面的硬约束。

三种类型（primitives）：

| 类型 | 输入 criteria | 输出 |
|---|---|---|
| **Choice** | 2–255 个候选，每个是 `候选名: 描述` | 每个候选的完整概率分布 + `confidence` |
| **Score** | 2–10 个**有序**等级描述 | 每级概率分布 + 期望分 `Σ i·p_i` + legend |
| **Noul**（SDK 里叫 Boolean） | 可选 true/false 说明 | 单个概率值 `P(是)`，没有独立 confidence |

![Jev 三种 primitive 的输入输出示意](/assets/img/posts/20260919-jev/002_io.png)

这套接口里有几个设计挺容易被忽略。

首先，**Choice 的问题 ID 不会进入模型**。比如你把一个问题命名成 `route` 或 `urgency`，这个名字只负责在返回结果里对上答案，模型真正看到的是 `instructions` 和候选描述。所以问题不能只写一句“请判断”，指望模型从 `route` 这个 key 猜出你想问什么。

其次，**Score 不会把等级数字喂给模型，也不会让某一级看到相邻等级的描述**。假设四档严重程度分别叫 0、1、2、3，模型判断“核心功能受阻”时，并不知道它前面是“次要功能受阻”、后面是“服务完全中断”。每一档先独立得到分数，最后才把概率按顺序加权成期望值。这样做是为了避免模型只靠“第 3 档听起来比第 2 档严重”这种位置线索来猜。

最后，**Noul 没有单独的 confidence 字段**，只返回 `P(true)`。Choice 和 Score 的 confidence 也不是模型额外预测出来的另一个数，而是根据最终概率分布算出来的。

上下文预算：state + 全部 questions 合计 64k token，state + 最长单个 question 32k token；定价 **输入 $0.042/百万 token，输出免费**（本来就不产生输出 token）。

confidence 公式（来自 MIT 协议的 LLM adapter，是 adapter 实现不是服务端证明，但可合理参考）：

```text
choice_confidence = (max(p) - 1/K) / (1 - 1/K)      # K 是候选数

m = argmax(p); d = Σ p_i * |i - m|; d_uniform = (1/K) * Σ |i - (K-1)/2|
score_confidence = max(0, 1 - d / d_uniform)
```

所以这里的 **confidence 衡量的是“这组概率有多集中”，不是“这次答案有多大概率正确”**。分布越接近 one-hot，confidence 越接近 1；越接近均匀分布，就越接近 0。这两个概念不能混在一起：一个模型完全可能非常自信地选错。

接口讲得很清楚，但模型内部怎么实现，官方基本没说。到目前为止，下面这些信息都没有公开：

- 网络具体结构、参数量（官方只说"不是小模型，也不是传统 LLM"，没给数字）
- **RLCD** 的 reward 设计、loss、采样算法、**训练数据规模和来源**
- 训练代码本身

官方倒是讲了 workflow eval 怎么做：ground truth 来自 GPT-6 Astra 和 Claude Fable 5.1 高推理模式的共识标注，Jev 在这套 eval 上的分数约为 67.8%，而且这些评测集不进入训练集。但这只能回答“怎么评”，回答不了“怎么训”。模型结构和训练流程这块，只能借助 NanoJev 看一种可能的实现。

## 3. 开源实现：NanoJev 怎么把这套接口跑起来

NanoJev 是基于 Qwen3-0.6B 做的一套独立实现。它复现的是 Jev 的输入输出方式，不是 Jev 的真实内部结构。下面的代码都来自 NanoJev 的 [`scripts/`](https://github.com/TianyuCodings/NanoJev/tree/main/scripts) 目录。

### 3.1 共享的部分：一个 backbone + 一个 decision head

NanoJev 没有给 Choice、Score、Boolean 各做一个模型。三种问题共用同一个 backbone 和同一个 decision head，区别主要发生在输入怎么拼、logit 怎么整理，以及最后怎么解释概率。

传统自回归 LLM 最后一层是词表大小的 LM head，输出 `[batch, seq_len, vocab_size]`。NanoJev 把这层整个换掉：骨干用 HuggingFace 的 `AutoModel`（不是 `AutoModelForCausalLM`）加载 Qwen3-0.6B——`Qwen3Model` 只返回 hidden states `[B, N, d_model]`，不接词表投影，省下一大块显存计算。骨干后面接一个极简的 **decision head**：`LayerNorm(d_model) + Linear(d_model, 1)`。每个候选走完 backbone 后，取它最后一个有效 token 的 hidden state 过这个 head，拿到一个标量 logit；同一个问题下所有候选的 logit 拼起来做一次 softmax，就是完整概率分布。

![传统自回归解码 vs Jev/NanoJev 的并行决策范式](/assets/img/posts/20260919-jev/001_paradigm.png)

最直白的收益是**删掉了解码循环**：不管候选多少个，都只需要一次 forward。NanoJev README 给的实测数字是"6 个状态 · 18 个问题 · 44 条候选路径 · 1 次 backbone 前向"。

这也引出了一个很关键的问题：**最后明明只有一个 `Linear(d_model, 1)`，为什么输入 2 个候选时能输出 2 个概率，输入 255 个候选时又能输出 255 个？**

答案是：它不是用一个固定的 255 维分类头，而是用**同一个标量打分器，对每个候选各打一次分**。

```text
候选 A → backbone → decision head → z_A
候选 B → backbone → decision head → z_B
候选 C → backbone → decision head → z_C

softmax([z_A, z_B, z_C]) → [p_A, p_B, p_C]
```

这次请求有 3 个候选，就产生 3 个 logit，softmax 后自然得到长度为 3 的概率向量；下一次有 20 个候选，就产生 20 个 logit，输出长度自然变成 20。**变化的是送进打分器的候选条数，不是模型参数，也不是最后一层的输出维度。**这和固定类别分类器有本质区别：普通分类头通常是 `Linear(d, 固定类别数)`，类别数在训练时就焊死了；NanoJev 的 head 永远只是 `Linear(d, 1)`，所以候选集合可以在请求到来时临时给。

一个 batch 里不同问题的候选数也可以不同。假设三个问题分别有 2、5、20 个候选，代码会先按这批最大的 `kmax=20` 补齐成矩形张量：

```text
问题 1：[z1, z2, PAD, PAD, ...]   valid = [1,1,0,0,...]
问题 2：[z1, z2, z3, z4, z5, ...] valid = [1,1,1,1,1,0,...]
问题 3：[z1, z2, ... z20]          valid = [1,1,...,1]
```

padding 位置会在 softmax 前被 mask 成一个极大的负数，因此概率接近 0；最后再按每个问题真实的候选数切回来。于是三个问题分别返回长度 2、5、20 的分布，而不是都返回 20 个值。

NanoJev 还专门用同一个 checkpoint 测过 `K=2/5/20/64/255`：合并后的输出张量是 `[5,255]`，拆回每个问题后，概率向量长度分别就是 2、5、20、64、255，且各自和为 1。这里要注意，**这个测试只证明形状和概率归一化能动态变化，不代表模型面对训练时没见过的 255 个候选，判断质量仍然不会下降。**候选越多，计算和显存也会跟着增加；NanoJev 目前只是把所有候选路径放进同一次 batched forward，并不是 255 个候选和 2 个候选成本一样。

三种类型的输入拼法在这一步就分岔了：

```python
# scripts/train_toy_decisions.py
# def load_examples(path, tokenizer, max_length)  第 28 行
for qid, q in row['questions'].items():
    typ = q['type']
    if typ == 'boolean':
        ids, texts = ['false', 'true'], ['The proposition is true.']
    elif typ == 'choice':
        ids = list(q['criteria']); texts = [f"{key}: {q['criteria'][key]}" for key in ids]
    else:  # score
        ids = [str(i) for i in range(len(q['criteria']))]; texts = q['criteria']  # 绝不注入等级数字
    prefix = ...  # State: + Question type/instructions
    leaves = [prefix + tokenizer.encode(f"Candidate:\n{t}\nDecision:") + [eos] for t in texts]
```

**输出 `leaves`**：长度等于该问题候选数的 token id 序列列表，每条都重复了完整的 `State:` + `Question:` 前缀，只在 `Candidate:` 部分不同（这个重复正是 3.7 节要处理的问题）。**Boolean 只生成一条路径**（"命题为真"），这一点先记住，3.3 节会解释为什么——这也是它和 Qwen3-Reranker 撞车的地方。代码里有个硬约束：`max(map(len, leaves)) > max_length` 直接抛异常，不做静默截断，宁可训练失败也不悄悄喂错数据。

forward 的核心一段（`class DecisionModel.forward`，三种类型走的是完全一样的代码，还没有分支）：

```python
# scripts/train_toy_decisions.py
# class DecisionModel(nn.Module)
# def forward(self, examples, pad_token)  第 104 行
paths = [ids for ex in examples for ids in ex['leaf_tokens']]   # 打平成一个大列表
tokens, attention = pad_to_batch(paths)                          # [P, W]
hidden = self.backbone(input_ids=tokens, attention_mask=attention).last_hidden_state  # [P, W, 1024]
leaves = hidden[torch.arange(len(paths)), lengths - 1]           # 每条路径取最后一个真实 token, [P, 1024]
# 重新按 examples 分组回 [num_questions, kmax, 1024]，再过 head
h = regroup(leaves, examples)
z = self.scalar(self.norm(h)).squeeze(-1).float()                 # [num_questions, kmax]
```

举个数：一个 batch 里有 3 个问题（4-Choice / 2-Boolean / 5-Score），`paths` 长度就是 `4+2+5=11`，**这 11 条路径被塞进同一次矩阵运算**——这就是"并行"的字面含义：不是多线程,是把本该分别推理的多条路径合并成一次 forward。`hidden` 只在真实长度对应的位置取值（不是最后一列，因为大多数行末尾是 padding）。`regroup` 把打平的 `[11, 1024]` 按 examples 顺序还原回"每个问题一组"，`z` 最终形状 `[3, 5]`（3 个问题，最多 5 候选）——**到这一步为止，Choice/Score/Boolean 用的是同一套 `norm`+`scalar` 参数，代码里没有任何 `if type==` 判断**，下面才开始分叉。

### 3.2 Choice：独立打分的天花板（IIA），以及 set-attention 怎么修

如果每个候选都是独立打分，会有一个数学上绕不开的问题：**IIA（Independence of Irrelevant Alternatives）**——两个候选的相对胜率之比 `p(a)/p(b) = exp(z_a - z_b)` 只由 `z_a, z_b` 决定，跟候选集里加了什么第三个候选完全无关。**这不是 Jev 独有的**，1.1 节说的 rerank 模型独立打分再排序,同样是 IIA 重灾区。

NanoJev 举的反例："从集合里选一个最接近均值的数字"。`{0,4,5}` 里该选 4；换成 `{0,4,5,100}` 均值变了,该选 5。如果 4 和 5 的 hidden state 都不知道对方、更不知道 100 的存在，它们的相对打分不可能因为多了个 100 而翻转——这是"候选间互相看不见"这个设计本身的天花板,不是训练不够。

方案是**给 Choice 单独加一个 set-attention head**，让同一问题下所有候选的 hidden state 互相 attention 一次，吐出修正量加到 `z` 上（只用在 Choice，Score 明确不用——官方 Score 语义就是每级独立判断，不看相邻等级）：

```python
choice = [i for i, ex in enumerate(examples) if ex['type'] == 'choice']
u = self.set_project(concat(h[choice], log(候选数)))
mixed, _ = self.set_attention(u, u, u, key_padding_mask=~valid[choice])  # nn.MultiheadAttention(128, 4)
delta = self.set_output(tanh(u + mixed)).squeeze(-1).float()
z = z.index_add(0, choice, delta)
```

**关键细节**：`set_output` 的权重零初始化，训练刚开始 `delta` 全是 0，网络初始行为等价于完全没有 set-attention——之后再靠训练慢慢学要不要用它，是个很实用的稳定训练技巧。最终 `p = softmax(z)`，`z` 是修正过的这一份 logit。

### 3.3 Score 与 Boolean：不加新头，只是后处理和数据构造上的技巧

Score 在 `z = self.scalar(h)` 之后**什么都不做**——不进 set-attention，也没有覆写逻辑。它和 Choice 的区别只在**推理拿到 softmax 之后**：Choice 直接 `argmax`，Score 把等级下标当权重算期望分 `score = Σ k·p_k`。

Boolean 更微妙：3.1 节说过它只生成**一条**候选路径，`z` 里只有一个真实数字。真正把它变成"是/否"两个候选，靠 forward 最后几行的覆写：

```python
# false 分支固定是 0，true 分支是模型算出来的 logit
out_boolean = torch.stack([z[i,0] * 0, z[i,0]])
# 等价于 p_true = sigmoid(z_true - z_false) = sigmoid(z - 0)
```

**它没有单独训一个 sigmoid head，而是把"是/否"当成两候选的 Choice 特例，固定把 false 分支的 logit 钉在 0，只让模型学"true 分支比 false 分支高多少"**。这跟 Qwen3-Reranker 用 `yes`/`no` 两个 token 的 logit 做 softmax 归一化,本质是同一个技巧的两种实现——一个钉死一个分支为常数，一个直接拿两个真实 token 的 logit 做差，殊途同归都是把二分类塞进一次 softmax/sigmoid。

三种类型最后收尾都走同一个函数（`predict_toy_decisions.py` 的 `answer_from_probabilities`）：校验概率合法、找 `argmax`，只在打包结果时按 `type` 分叉——Choice 给 `choice=候选名`，Score 多算一行期望值，Boolean 取 `p_true=probabilities[1]`。**三种 primitive 共享机制、只在收尾分叉**，这一处体现得最干净。

### 3.4 串起来看

```text
3 个问题（4-Choice/2-Boolean/5-Score），共 11 条候选路径
  → tokens[11,55] → backbone（唯一一次真正的 forward，三种类型共用）
  → hidden[11,55,1024] → 取每行末位 → leaves[11,1024]
  → 按 examples 重新分组 → h[3,5,1024] → norm+scalar（共享参数）→ z[3,5]
  → 仅 Choice：set-attention 修正 z；Boolean：固定 false=0 覆写 z
  → masked_fill + softmax(-1) → 3 个问题各自的候选概率分布
  → Choice: argmax / Score: Σk·p_k / Boolean: p_true
```

全程只有一次 backbone forward，没有任何自回归解码步骤——`benchmark` 函数打点报告里专门写了一行 `'autoregressive_decode_steps': 0`，把这个特征当核心卖点直接打在性能报告里。

### 3.5 数据集是怎么构建的

官方这块完全是空白——训练数据的构成、规模、来源，TypeSafe 一个字没披露。这里只能讲 NanoJev 自己怎么造数据,**同样不代表 Jev 真实训练数据长这样**。

小规模的玩具数据集（[`scripts/build_toy_decisions.py`](https://github.com/TianyuCodings/NanoJev/blob/main/scripts/build_toy_decisions.py)）是纯 Python 生成的客服工单路由场景：6 种 route × 6 种退款状态 × 4 种影响等级组合出事实空间,固定切成 **train / dev / calibration / test / ood 五个分片**。OOD 分片刻意放了一个**完全不同的任务家族**（权限申请类工单），不是简单地从同一分布里多留一些没见过的样本——这是在测**跨任务家族**的泛化，比"同分布留一手"严格得多。

代码里的 `validate_records()` 做了一堆防泄漏检查：分片之间不能有重复的 state ID、不能有相同的事实组合（fact-group）跨分片出现、模板文字也不能跨分片重复；中文 state 文本限长 100 字、criteria 限长 40 字；**真正喂给模型的 `questions` 字典里只有 `type`/`instructions`/`criteria` 三个字段**,任何 metadata 或标准答案都不会泄漏进模型输入。

更大规模的迷宫/贪吃蛇数据集（[`docs/SCALED_GAMES.md`](https://github.com/TianyuCodings/NanoJev/blob/main/docs/SCALED_GAMES.md)）用 `build_scaled_games.py` 生成，训练用 8×8/16×16/32×32 三种棋盘尺寸，**50×50（可选 64×64）整块留作 OOD，训练阶段完全不出现**——这是下一节泛化能力的核心机制。迷宫有四种拓扑家族（走廊、树状、环路、随机障碍物）增加结构多样性；D4 对称（旋转/镜像）等价的布局会被归到同一个"来源组"，避免近似重复的样例被分到不同分片里造成隐性泄漏；贪吃蛇按尺寸+固定种子分组。冻结版本的数据统计是 589 个 policy state / 3195 个 question，另有 2356 个 event state。

### 3.6 开源版本怎么训练，又怎么保证泛化能力

**训练配方**（[`scripts/train_toy_decisions.py`](https://github.com/TianyuCodings/NanoJev/blob/main/scripts/train_toy_decisions.py) 的 `main()`）：AdamW，backbone 和 decision head 用**不同学习率**（backbone 2e-5，head 2e-4，head 学得快是因为它是随机初始化的新参数，backbone 是预训练过的，要小步微调），weight decay 0.01，梯度范数裁剪到 1.0；forward 用 BF16 autocast 但参数和 optimizer state 存 FP32（BF16 省显存，FP32 optimizer state 保证更新精度不被 BF16 的低精度拖垮）；可选先跑一段**只训 head、冻结 backbone** 的热身阶段（`--head-steps`），再解冻整个网络一起训；checkpoint 按 dev 集上最低的 NLL/CE 挑，不是训练 loss 最低那个；五个分片必须全部非空,少一个就直接报错退出。

**训练目标**上 NanoJev 有一份独立的实验（[`docs/RLCD_EXPERIMENT.md`](https://github.com/TianyuCodings/NanoJev/blob/main/docs/RLCD_EXPERIMENT.md)），**文档里说得很清楚：这是一个独立研究候选方案，不是还原出来的官方 RLCD 配方**。他们试的是一种"成对适当奖励"策略梯度目标，理论上站在 proper scoring rule 之上（引用 Gneiting 2007 JASA 的结果，证明这个目标的梯度期望等于 `‖p-q‖²` 的梯度），在 CPU 合成任务和基于 Qwen 的迷宫/贪吃蛇碰撞事件预测任务上都做了对比：**成对策略梯度、直接 Brier loss、直接交叉熵三者效果相近，都明显好于随机**；但一个"只看对错不看概率、纯 REINFORCE"的朴素目标效果明显更差——这是一个典型的 reward hacking 陷阱：模型学会了"猜对"而不是"给出校准的概率"。

泛化能力主要靠数据切分来检验，而不是靠一个特殊算法来保证：训练只放 8×8、16×16、32×32 的棋盘，50×50 完全留到 OOD 测试。OOD 就是训练分布之外的数据，这里具体指模型训练时没见过的棋盘尺寸。

不过这个结果不能往大了说。`docs/MODEL_EDGE_RESULTS.md` 明确写着，这个小规模的三迷宫实验不足以证明模型能泛化到任意 50×50 地图。在这组 pilot 里，真实 Jev API 的表现甚至不如“完美局部几何”基线，和部分简单基线相比也没有明显优势。它证明的是这套训练与评测流程可以跑通，不是“模型已经具备很强的通用泛化能力”。

### 3.7 更进一步的推断：共享前缀树 attention（尚未落地，仅设计规格）

3.1 节的重复问题：每条候选路径都各自拼了一遍完整的 `State:` 前缀。NanoJev 的 research 文档提了一个更激进的设计（**明确标注未落地**）：把一次请求的所有 token 组织成一棵树——根是 `State`（所有 question 共享），子节点是各个 `Question`，孙节点是各自的 `Candidate + Decision:`。

![共享前缀树的结构示意](/assets/img/posts/20260919-jev/003_tree.png)

只需一次 forward，靠自定义 attention mask 保证树的语义：token `i` 只能看到自己的严格祖先节点,或同节点内更靠前的位置——**兄弟分支之间完全没有边**，普通下三角 causal mask 做不到这一点。判断"是不是祖先"靠 DFS 给每个节点标一个 `(tin, tout)` 区间，退化成一次区间比较,不用存 `N×N` 布尔表。position id 也不是简单递增,而是"从根到它的路径深度",不同分支可以有相同的 position id,因为 mask 已经把兄弟隔开了。

文档里列了几个还没验证的风险：`attention_mask=None` 时 HuggingFace 会用 position id 跳变自动推断 packed sequence 边界,这个机制会误伤树的祖先连接,必须显式传 mask；树的 token 数比打平后少，不代表一定跑得更快，因为 dense attention 看的是有效边数；真正的收益要换成 FlexAttention 的 BlockMask 才可能兑现,SDPA/eager 上的 dense mask 只是正确性实现。**这部分是"值得关注的方向"，不是"已验证的结论"**。

## 4. 小结：Jev 和现有分类方法到底差在哪

读到这里再回头看，Jev 解决的并不是“模型能不能分类”——BERT 时代就能做，今天拿任意 LLM 回答 A/B/C 也能做。它真正想解决的是另一件事：

> **能不能让一个理解自然语言指令、候选集合每次都可以变化的模型，像专用分类器一样直接输出概率，而不是先生成文字再解析。**

放在一起看，差别就清楚了：

| 方法 | 候选从哪里来 | 候选数 | 怎么得到答案 | 主要问题 |
|---|---|---:|---|---|
| 固定分类头 | 训练时写死 | 固定 | 一次输出 N 类概率 | 换类别就要改 head、重新训练 |
| LLM 生成 A/B/JSON | 请求时给 | 可变 | 自回归生成后解析 | 有解码成本和格式失败 |
| 受限解码 | 请求时给 | 可变 | mask 非法 token 后生成 | 长文本候选、多 token 候选处理麻烦 |
| Cross-encoder reranker | 请求时给 | 可变 | 每个候选独立打分 | K 个候选通常要做 K 次独立判断 |
| Jev / NanoJev 式决策 | 请求时给 | 2–255 | 每候选一个标量 logit，再联合 softmax | 候选越多计算仍越大，效果依赖专门训练 |

其中最关键的就是前面解释的动态候选：**head 始终只输出一个标量，来几个候选就运行几条候选路径，再把当次产生的 K 个标量放在一起归一化。**所以它不需要提前知道这次是 3 类还是 255 类，也不需要准备一个固定 255 维输出层。

但这里还要把官方 Jev 和 NanoJev 分开。官方只公开了接口、上下文限制、价格和部分评测，具体网络结构、参数量、RLCD 训练方法和训练数据都没有公开。NanoJev 的“Qwen3-0.6B + scalar head + Choice set-attention”只是一种能跑通相似接口的独立实现，**证明这条技术路线可以这样做，不证明真实 Jev 内部就是这样做的。**

NanoJev 同样还有一个很现实的性能缺口：它虽然把所有候选打包进一次 batched forward，但每条候选路径仍然重复携带完整的 state 和 question。所谓 tree attention 目前只是设计规格，还没有变成已经验证的加速结果。因此“没有自回归解码”和“候选数量几乎没有成本”是两回事——前者已经做到，后者没有。

所以这类模型更准确的定位，不是一个神秘的新分类器，而是 **workflow 的决策层**：上游把当前状态和合法选项交给它，它返回一个可以直接用于执行、拒绝或升级处理的概率分布。智能家居、Agent 工具选择、检索重排和游戏控制看起来完全不同，最后都能归到这个接口上。这才是一个简单分类任务突然变得有价值的原因。

顺带扯一句题外话:这类"用 decision head 替代生成"的思路,是在**判断这个任务压根不需要生成**,而不是优化生成过程本身。这两年一个挺明显的趋势就是越来越多团队开始琢磨"这个子任务到底要不要走完整自回归"。我们把 LLM 架构自动化、模型压缩这些相关积累整理成了一本书,第 9 章正好讲 LLM 驱动的 AutoML 和 LLM Agent 结合的方向,跟这篇聊的"任务专用化改造"角度不同但目标相近。
