MICRO’26 | EdgeXpert：MoE 加上推测解码，为什么反而更费内存带宽？

原文：EdgeXpert: An Edge Device for Memory-Efficient LLM Inference with Mixture-of-Experts and Speculative Decoding

1. 两个省开销的方案，放在一起却更费了

在手机这类设备上跑大模型，有个很现实的麻烦：计算单元好不容易忙起来，下一批权重还没搬到。

模型权重主要放在芯片外部的 DRAM 里，真正计算时，要先搬进芯片内部的小块快速存储。模型一大、带宽一小，生成文字就很容易变成“算得快，等得久”。

MoE 和推测解码，恰好都能缓解这个问题，只是思路不同。

MoE 想少用一点权重。 它把模型中处理 token 特征的前馈网络分成许多个 expert，也就是专家网络，每个 token 只挑少数几个来算。负责挑选的是 router，可以理解成给专家打分的路由器。这样，总参数量可以很大，单个 token 实际使用的参数却少得多。这类架构叫 Mixture-of-Experts，混合专家，Qwen3-30B-A3B、DeepSeek-V2-Lite 都属于这一类。

推测解码则想让一次权重读取多干一点活。 普通生成是大模型算一轮、输出一个 token，再算一轮、再输出一个。推测解码先让一个便宜的小模型猜几步，再交给大模型一起验证。小模型叫 draft model，负责起草；大模型叫 target model，负责把关。如果一轮能接受好几个 token，就不用为了每个输出都重新跑一遍大模型。

一个少用权重，一个摊薄读取成本，放在一起应该更省吧？

结果并不一定。EdgeXpert 在 Qwen3-30B-A3B + EAGLE-3 配置中发现，普通逐 token 解码每层用 8 个专家；改成一批候选一起验证后，每层每轮平均要用 52.1 个不同专家。一轮虽然平均推进了 4.3 个 token，专家数量却涨到了约 6.5 倍。没有针对性优化时，整体能耗反而增加了 24.3%。[1，§I]

这组数字把问题点得很清楚：每个 token 只用几个专家，不代表一批 token 加起来也只用几个。

下面这张图，左边是一次处理一个 token，右边是一批候选一起验证。看每个 token 各自的路由还很稀疏，但把右边所有路由合起来，需要搬进来的专家就多了。

原本想用更多候选摊薄大模型开销，结果候选各找各的专家，把要读的权重也一起撑大了。少跑几轮省下来的，可能还抵不过每轮多搬的。

EdgeXpert 这篇 MICRO 2026 的工作，就是从这个矛盾出发。它没有简单地说“专家再剪一点”，而是追着权重的读取过程往下看：哪些专家可以复用？专家里面哪些通道没必要读？少读之后损失的信息，又能不能利用已经读进来的数据补一点？

要理解后面这几个设计，先把这笔访存账算清楚。

2. 真正要算的，是生成一个输出 token 得搬多少数据

2.1 省内存容量，和省内存带宽，不是一回事

“省内存”这个说法太宽了。

把权重量化到 4-bit，可以让模型更容易装进设备；把专家卸载到 CPU 内存，可以省 GPU 显存。但模型装得下之后，每生成一个 token 还要读多少数据，是另一个问题。

EdgeXpert 主要研究后者：从片外 DRAM 到芯片内部的数据搬运。论文把它叫作 EMA，external memory access，片外内存访问。实验中的片外内存是低功耗移动内存 LPDDR4X，带宽为 16 GB/s。[1，§II-A、§V-A]

后面看到“EMA 降了多少”，可以先理解成“从芯片外面搬进来的权重少了多少”，而不是“模型总参数少了多少”或者“GPU 显存省了多少”。

2.2 几个很小的集合，加起来也可能很大

假设每个 token 选两个专家：第一个选 A、B，第二个选 B、C。各自都只用两个，但放在一起算，需要读的是 A、B、C 三个。

候选继续增加，而且大家选得越来越不一样，专家并集就继续扩大。

用一个式子记下来。候选 $t$ 选的专家集合是 $\mathcal E_t$，一轮有 $M$ 个候选，那么验证要处理的专家是：

\[\mathcal E_{\mathrm{verify}}=\bigcup_{t=1}^{M}\mathcal E_t.\]

这里的并集，就是把重复专家只算一次。如果这一层总共有 $E$ 个专家，每个候选选 $k$ 个，那么：

\[k\leq |\mathcal E_{\mathrm{verify}}|\leq\min(E,Mk).\]

最理想的情况，所有候选都选同一批专家；最不理想的情况，各选各的，把这一层的大部分专家都叫来了。

推测解码的收益，取决于这份额外开销能不能被最终接受的 token 数摊掉。记一轮验证搬运的字节数为 $B_{\mathrm{verify}}$，起草的开销为 $B_{\mathrm{draft}}$，一轮平均推进 $N_A$ 个输出 token，可以写一个简化的账：

\[B_{\mathrm{per\ output}} \approx\frac{B_{\mathrm{verify}}+B_{\mathrm{draft}}}{N_A}.\]

分母变大当然是好事，但 MoE 的分子也在跟着涨。只看“一轮接受了几个”，还不能判断是否划算。这个式子暂时只算数据量，实际时延还要考虑计算、并行和控制开销。

2.3 为什么验证了 64 个候选，却只推进了几个 token？

因为这些候选不是一条长达 64 个 token 的续写，而是一棵有分支的候选树。

例如，当前前缀后面可能接 is → my → car，也可能接 is → the → seat。draft 把几种可能都猜出来，target 一起验证，最后只沿其中一条通过验证的连续路径往前走。

下面这张图从左往右看：先起草分支，再打包验证，最后保留路径。重点看树的宽度和深度：宽度代表同一步有多少种猜法，深度才代表往后猜了几步。

图里不同路径不能相互偷看历史。实现上通过 tree attention 限制每个节点只看到原始前缀和自己路径上的祖先。这样能把多个分支放进一次验证，又不会把另一条分支当成已经生成的文字。

所以，“每轮 64 个候选”和“平均接受长度 4.3”并不冲突。前者是这轮验证了多少个节点，后者是最终平均向前走了多少个 token。每个深度最多留下一个候选，后面的分支也可能全部被拒绝。[1，§II-B]

到这里，EdgeXpert 面对的任务就明确了：尽量保住一轮能推进的长度，同时把这一轮读入的专家权重压下来。

输入和输出两个阶段的问题还不完全一样。输入阶段已经知道完整 prompt，可以提前决定哪些 token 值得多分资源；输出阶段不知道哪个候选会留下，就得在保留有效信息与减少读取之间取舍。这也对应了论文的两部分设计。

3. 处理输入时，让次要 token 少找几个新专家

3.1 为什么先判断 token 重要性？

模型收到问题后，要先把整个输入处理一遍，建立后续生成所需的历史状态。这一步叫 prefill。之后逐步输出文字，叫 decode。

prefill 一次处理很多输入 token。如果每个 token 都独立选自己的 Top-k 专家，也就是 router 分数最高的 $k$ 个，专家并集同样容易变大。

最直接的省法，是让每个 token 少用几个专家。但输入中有些位置承载了关键约束，比如问题中的数字、否定词、任务要求；这些地方也一刀切减预算，容易省过头。

EdgeXpert 因而先做一件事：估计输入里哪些 token 更值得保留原有计算，再让其他 token 尽量复用已经选过的专家。

这里没有直接使用 target 的 attention，因为等 target 算完，再来决定它应该少读什么，已经晚了。作者额外用了约 23M 参数的 all-MiniLM-L6-v2 小 encoder，先看一遍完整输入。[1，§III-A、§IV-B]

Encoder 的 attention 可以同时看前后文。它有一个用于汇聚序列信息的特殊位置 [CLS]；作者取最后一层中这个位置对其他 token 的 attention，跨多个 attention head 平均，作为重要性分数。可以把它理解成一个便宜的优先级提示：它不是替大模型回答问题，也不是保证识别出所有关键 token。

下面先看小 encoder 如何产生分数，再看分数对应的三组 token。major、minor、trivial 分别表示较重要、次要和更次要，后面会给它们不同的专家预算。

这个分组不删除输入文字，也不改变原始顺序。它改变的是：到了 MoE 层，这个 token 可以使用多少专家，以及优先使用哪些专家。

小 encoder 和 target 的分词方式可能不同，同一段文字不一定切成一样的 token。公开代码通过字符区间的重叠关系映射分数，取重叠 encoder token 分数的最大值，而不是把两个不同长度的向量硬对齐。[9，moe_prefill_utils.py]

3.2 候选范围放宽，实际执行反而减少

有了分组，下一步就是分预算。

论文 Qwen3 配置原本每个 token 选 8 个专家。major 保持这个预算，先让它们选完，把选过的专家编号放进一个集合。轮到 minor、trivial 时，就在自己的候选中优先寻找这个集合里的专家。

这里要区分两个数：候选范围 $k$ 和 最终执行数量 $n$。

分组 从排名前多少个专家里选，$k$ 最终执行几个，$n$
major 8 8
minor 10 6
trivial 12 4

为什么越不重要，候选范围反而越大？不是要它执行 Top-12，而是让它在前 12 名里找 4 个。范围宽一点，更容易遇到前面已经选过的专家，就能少引入几个新专家。

下面这张图把“放宽候选”和“减少执行”画在一起。看 minor、trivial 的选择，不是简单截掉排名靠后的项，而是在保留最重要路由的同时，偏向已经出现过的专家。

走一个缩小版例子会更直观。假设前面的重要 token 已经选出了 A、C、D。现在某个次要 token 的专家排名是 B、A、E、C、D、F，预算是 3 个。

独立选 Top-3，会选 B、A、E；EdgeXpert 先保留分数最高的 B，再从已有集合里选到 A、C。这样变成 B、A、C，省掉了为了 E 再读一次权重。

B 仍然是新专家，所以它不是强迫所有 token 用同一批。它只是保住 Top-1，再让剩下的选择多考虑一点复用。minor 处理后会更新集合，trivial 还能接着复用。[1，Algorithm 1、Table III]

顺带区分一下，论文这里共享的是专家编号集合，不代表整批权重都缓存到了片上，也不是 MoE 架构中所有 token 必经的 shared expert。

3.3 多跑一个 encoder，省下的值得吗？

这套方案当然也有额外开销：小 encoder 要算，token 要分组，路由也要调整。

作者并没有直接把 token 全局排序，而是按分数阈值分组，硬件一次处理 128 个 token，通过三级流水线推进；更长输入按块处理，避免为了跨块排序付出太多成本。[1，§IV-B]

下图把新增开销和省下的专家读取放到一起。先看原方案与新方案的总量，再看新方案里 encoder 占多大。

图中的 Qwen3 例子，prefill 专家 EMA 从 5.86 GB 降到 2.60 GB，减少了 55.7%；小 encoder 约占图中新方案 EMA 构成的 0.4%。在这个配置下，额外看一遍输入，换来了更多的权重读取节省。这里下降的是专家读取量，完整系统的时延与能耗还要到实验部分再看。

预算也不是凭感觉定的。作者用一批校准样本，对比改路由前后 MoE 输出的偏差，以及激活专家数减少了多少，再选折中点。输出偏差用归一化均方误差衡量：差值的平方和除以原输出的平方和，越低越接近原模型。专家数则是读取需求的近似指标，具体字节量还与专家大小有关。

因此，prefill 这部分可以概括成：让重要 token 先确定一批值得读的专家，次要 token 再在自己的候选范围内搭一部分便车。

但到了 decode，仅仅控制专家数量还不够。因为即便两个候选进了同一个专家，它们想用的内部权重也未必相同。

4. 生成阶段：每个候选都少算了，为什么权重还是没少读？

4.1 从专家往里看，还有一层“并集”问题

专家内部仍然是矩阵计算。一个输入向量有很多分量，通常把这些分量叫作通道；保留某个输入通道，就要用到权重矩阵里与它对应的一片权重。

已有的优化会根据激活大小，跳过贡献较小的通道。用一个 mask 标记保留位置，1 表示计算，0 表示跳过。

问题来了：两个候选各跳过一半，不代表它们合起来也只需要一半权重。

比如，候选 A 保留通道 0、2，候选 B 保留通道 1、2。各自只算两个通道，硬件却要读通道 0、1、2 对应的权重。只有两个候选都不用的部分，才能不读。

下面看原文的例子。按各 token 的 mask 数计算量，确实少算了很多；但把 mask 合起来看，权重读取仍然很满。

图里计算减少了 62.5%，权重 EMA 却只减少了 25%。这组数是示意例子，但它说明的问题很普遍：少算看每个 token 自己，少读要看所有 token 合起来。[1，§IV-C]

这也是 EdgeXpert 在前序硬件 SMoLPU 之上继续做优化的原因。SMoLPU 已经先剪专家、再剪专家内部通道，但逐 token 剪完之后，仍然可能留下一个很大的通道并集。

4.2 为什么把候选按树的深度分组？

要缩小这个并集，先得找到哪些候选适合放在一起处理。

回到前面的候选树。同一深度，指的是距离当前前缀相同的生成步数，不是 Transformer 的层数。

这些候选是在猜“同一个位置应该接什么”，往往有相近的语法或语义作用。原文举的 at、on、for 就是这样的候选。它们有机会选择相同专家，内部通道需求也可能有共性。

作者在 Qwen3 中观察到，在某些层与深度组合上，同深度候选共享至少 3 个所选专家的比例最高达到 88.4%。这为共同处理提供了依据，但不等于所有层都如此，也不意味着 88.4% 的通道都能共享。[1，§III-B]

还有一点更直接：验证结束后，同一深度最多只会留下一个候选。

看下图，上半部分为几个不同分支分别读取数据；下半部分只剩最终路径上的一个 at。其他分支需要的部分数据，在这一轮之后就没用了。

当然，验证前不知道哪个会留下，不能直接把其他分支扔掉。EdgeXpert 做的是一种近似取舍：优先保留这组候选共同需要、整体上更显著的通道，不再把所有独立需求照单全收。

论文把它叫作 depth-aware expert coalescing，可以理解成：进入同一个专家、处在同一候选深度的 token，合在一起决定要读哪些通道。

4.3 一个通道值不值得读，看两份分数

具体怎么判断？先不用记公式，想象给每个通道记两份账。

第一份账，统计这一组候选在该通道上的总激活幅度；第二份账，只统计原本被各自 mask 保留下来的幅度。前者看“这一通道总共有多少信号”，后者看“其中有多少属于原剪枝策略认为值得计算的信号”。

两份账都按 token 重要性加权。这个重要性来自 attention，与 prefill 的小 encoder 评分不是同一处机制。

把同一深度 $d$、同一专家 $e$ 的候选集合记成 $\mathcal T_{d,e}$。$x_{t,c}$ 是候选 $t$ 的通道 $c$ 激活，$a_t$ 是 attention 派生的权重，$m_{t,c}$ 是原 mask。两份分数是：

\[S_C(c)=\sum_{t\in\mathcal T_{d,e}}|x_{t,c}|a_t,\] \[S_S(c)=\sum_{t\in\mathcal T_{d,e}}m_{t,c}|x_{t,c}|a_t.\]

对于有实际需求的通道，如果 $S_S(c)>sr\cdot S_C(c)$，就倾向于加载；否则跳过。$sr$ 是 0 到 1 之间的阈值，越高越不容易通过，不是直接指定“保留多少比例”。[1，§IV-C]

例如，两个候选在某通道的加权幅度都是 5，但只有一个候选的原 mask 是 1。那么 $S_C=10$、$S_S=5$；取 $sr=0.9$，这个通道过不了门槛。如果两者都需要，$S_S=S_C=10$，就能通过。

这个例子也暴露了代价：第一个候选明明原本需要该通道，现在却可能失去它。它不是无损合并，而是用少读权重换一部分近似误差。

作者离线调阈值时，会检查最终被接受 token 的原通道需求被保留了多少，要求平均覆盖比例高于 75%。运行时并不知道未来谁会接受；“75%”只是校准时的集合覆盖要求，也不是准确率保证。

于是下一个问题自然就来了：如果少读让候选算得太不准，接受长度下降，不是又要多验证几轮吗？

5. 少读之后反而多算一点，为什么更划算？

5.1 已经搬进来的数据，不妨让更多候选用上

原来每个候选只计算自己 mask 里保留的通道。合并读取后，它能算的就只剩“自己想要的”和“硬件实际加载的”两者交集。

假设候选 A 原本需要通道 0、2，候选 B 需要通道 1、2。合并后只加载了 1、2，那么 A 就只能用通道 2，损失可能很大。

EdgeXpert 的处理有点反直觉：既然通道 1 的权重已经为 B 搬进来了，那也让 A 用上，不再坚持 A 原来的 mask。

这就是 computational calibration，计算校准。它把同组候选的计算范围扩展到已经加载的通道上，用更多乘加来减轻少读造成的输出偏差。

下面这张图分两步看。先看左侧到中间：合并后删去了一部分权重读取，对应候选也丢了信息；再看中间到右侧：读取集合不变，但给各候选补上已经加载通道的计算。

右下角 mask 中新变成 1 的位置，就是这些补算。它们没有要求新的片外权重读取，而是在复用已经付过搬运成本的数据。

回到 A 的例子，它现在可以计算通道 1、2，但丢掉的通道 0 没有回来。通道 1 也不是通道 0 的数学等价替代。这是一种经验有效的误差补救，不是重建原模型的精确输出。

5.2 接受长度保住了，少读才能真正兑现

为什么愿意增加乘加？因为在论文讨论的端侧工作点，搬权重往往比多算一点更贵。

如果为了严格少算，把每个候选都算得很差，target 一轮只能接受更短路径，就得多跑几轮，重新读取权重。这反而不划算。

下面看 Qwen3 的对比，重点把接受长度和累计 EMA 连起来看，不要只看每轮少读了多少。

单独做通道合并，平均接受长度从 4.3 降到了 3.6；加入计算校准后恢复到 4.4。完成同样长度的输出，所需验证轮数随之减少，累计专家 EMA 进一步下降。[1，§IV-C]

这就回到了第 2 节的式子：不只要压低分子，还要尽量保住分母。

EdgeXpert 最有意思的交换，是拿一部分便宜计算，去保住昂贵访存的收益。 但这个交换依赖硬件工作点；如果计算本来就很紧，额外乘加未必值得。

6. 算法里少用几个通道，硬件就真的少读了吗？

6.1 先决定不读，再发内存请求

还差最后一步。

在 PyTorch 中写一个 x * mask，能让某些通道不参与后续计算。但如果整个权重矩阵已经读进来了，再乘零，片外读取一字节也没省。

要把前面的想法落实，通道选择必须发生在权重读取之前，参与地址生成和内存请求。这也是为什么这篇论文要设计专用加速器，而不只是加一套模型近似策略。

下面这张图先看存储与计算的连接：权重从片外进入缓冲，再送往计算 cluster；分组和通道选择决定这条路径上究竟放行哪些数据。

EdgeXpert 有 8 个计算 cluster，以及 512 KB 的全局共享 SRAM。SRAM 是芯片内部速度快、但面积昂贵的存储；各 cluster 还有各自的输入和权重缓冲，512 KB 不是整颗芯片所有 SRAM 的总和。[1，§IV-A、Table V]

这个空间不足以常驻一批完整专家。论文举的 DeepSeek-V2-Lite 单个 4-bit 专家就约 4 MB，已经超过全局 SRAM。因此，执行更接近流式处理：载入当前专家的一块权重，让需要它的 token 尽量共用，处理完再往下走。

prefill 时，前面的路由复用让更多 token 使用同一专家；decode 时，按专家和候选深度汇总出读取集合，再只加载选中通道的权重。计算校准发生在这些数据已经可用之后。

这样，前面每个算法选择才在硬件中有了落点：不是只减少一张统计表里的非零项，而是真的少发了一部分内存请求。

6.2 选通道，还得选得适合连续读取

DRAM 不擅长今天抓一个数、明天抓另一个数。即便理论上保留权重很少，访问过于零碎，也可能省不下多少时间。

所以这里跳过的是输入通道对应的权重切片，并沿输出通道方向连续组织数据，而不是逐个标量随机加载。

用 Qwen3 的一个专家具体看一下。公开配置和 artifact 中，输入隐藏维度为 2048，专家中间维度为 768。输入经过 gate 和 up 两个投影，逐元素相乘后，再通过 down 投影回到 2048 维：[9][10]

\[X[T,2048] \longrightarrow \operatorname{SiLU}(XW_g^\top)\odot(XW_u^\top)[T,768] \longrightarrow Y[T,2048].\]

$T$ 是路由到当前专家的 token 数。比如有 4 个，就是 [4,2048]，不是把候选树里的全部 64 个节点都交给每个专家。SiLU 是非线性激活函数，$\odot$ 表示逐元素相乘。

按 PyTorch 的 [输出维, 输入维] 约定，gate/up 权重各是 [768,2048]，down 是 [2048,768]。剪 gate/up 的输入通道，作用在 2048 这一维；剪 down 的输入通道，作用在 768 这一维。两者不能混成同一个维度来理解。

硬件再根据读取方式重新安排物理布局。模型代码里的矩阵 shape 只说明逻辑维度，不等于权重在 DRAM 中如何排布。[1，§IV-A、§V-B]

另外，同一深度分到某专家的候选数会变化，用固定规模的归约硬件容易闲置。作者用可重构加法树汇总前面的通道分数，让硬件能同时处理多个小组。原文该单元时延减少 76.7%，这是局部汇总单元的改善，完整系统收益还得看端到端结果。

7. 效果怎样：访存省下来了，质量也有代价

7.1 这些数字来自什么硬件评估？

论文测试了 Granite-1B-A400M、OLMoE-1B-7B、DeepSeek-V2-Lite 和 Qwen3-30B-A3B，推测框架使用 EAGLE-3，每轮 64 个候选，最大树深度 6。

加速器按 Samsung 28nm 工艺、800 MHz 评估，激活为 8-bit、权重为 4-bit，也就是 A8W4；片外带宽为 16 GB/s。8K 乘加单元给出的峰值算力是 13.1 TOPS，即每秒约 13.1 万亿次基本运算。

这里需要保留一个重要前提：EdgeXpert 的结果来自逻辑综合、时序与功耗分析，再结合自定义模拟器估算，不是已经流片的手机芯片实测。 面积也包含利用率假设下的逻辑面积投影和 SRAM 宏面积。[1，§V-A]

7.2 先看完整任务，再拆首 token 与生成阶段

下面两张图分别看端到端时延和能耗。先在相同模型、相同输入输出长度内比较，再看不同配置下收益如何变化，别只取整张图最高的一根柱子。

时延结果反映了 prefill 与 decode 合起来的效果：少加载专家、少加载通道，以及校准后减少验证轮数，共同影响完成整段生成的时间。

能耗还要把新增计算算进去。下面这张图可以用来检查：为了省访存多做的分组、评分和补算，是否仍然值得。

论文相对其已有基线报告，端到端时延最高降低 56.3%，能耗最高降低 44.1%。这是最高收益，不是所有配置平均都能达到。[1，§V-B]

对照也做了硬件归一化：SMoLPU 归一到 800 MHz；EdgeMoE 的混合精度策略映射到专用后端，不是直接拿 Jetson 整板功耗比较；MoE-Pruner 采用对应的稀疏硬件映射，并关闭可选的剪枝后微调。因此，这组结果适合讨论统一后端下的效率，不能直接当成真实手机或 Jetson 上的胜负。

交互体验还要拆成两个指标：TTFT 是从请求开始到第一个输出 token 的等待时间；TPOT 是生成阶段平均每个输出 token 花的时间，都是越低越好。prefill 优化主要帮助前者，decode 优化主要帮助后者。

下图把这两部分单独列出，可以和前面两阶段的设计对应起来看。

DeepSeek-V2-Lite 的 TTFT 为 128.2 ms、TPOT 为 47.9 ms；Qwen3 分别为 120.3 ms、49.0 ms。论文采用 TTFT 小于 450 ms、TPOT 小于 50 ms 作为交互目标，在该评估条件下达到了这组目标。[1]

7.3 接受长度恢复了，不代表原模型质量完全恢复

前面已经看到，计算校准能把 Qwen3 的接受长度从 3.6 拉回 4.4。但生成时能接受更长路径，与最终答案是否和原来一样好，仍然要分开测试。

下面是 Qwen3 的部分质量结果。MT-Bench 衡量多轮对话质量；GSM8K 测小学数学应用题正确率，均越高越好。thinking 表示启用较长的中间推理过程。

Qwen3-30B-A3B 配置 MT-Bench GSM8K 非 thinking GSM8K thinking 平均接受长度
Baseline 8.8 72.8% 87.3% 4.3
加 prompt 级复用 8.7 72.8% 87.3% 4.3
再加通道合并，未加校准 5.8 66.8% 76.1% 3.6
完整 EdgeXpert 8.7 69.4% 88.0% 4.4

这里的 Baseline 已包含 SMoLPU 的基础剪枝，不是完全未经剪枝的原始模型。[1，Table IV]

读这张表，最明显的是两点。第一，单独通道合并省得太狠，质量和接受长度一起掉；第二，计算校准确实补回了大部分，但没有处处恢复。

非 thinking 的 GSM8K 仍下降了 3.4 个百分点。另两项测试也有损失：MMLU 衡量多领域知识问答正确率，从 76.2% 到 74.4%；PIQA 衡量物理常识问答正确率，从 79.2% 到 76.1%，都是越高越好。所以可以说“接近基线”，不能说“不掉精度”。

thinking 的 GSM8K 上升 0.7 个百分点，也不宜解释成近似计算提高了推理能力；论文没有提供支持稳定增益的统计证据。

还有一条边界要说清楚：标准推测解码在保持 target 验证分布、正确使用接受与修正机制时，可以保持输出分布不变。EdgeXpert 连 target 的路由和通道计算都改了，这份保证就不能直接沿用。 它靠任务评测约束近似代价，而不是对原模型无损。

8. 放回已有工作里，EdgeXpert 的新意在哪里？

现在理解了方法，再看 related work 就比较容易了。大家都在省数据搬运，但省的是不同地方。

缓存感知路由关心的是“哪些专家已经在快内存里，能不能优先用它们”。Mixture of Cache-Conditional Experts 在运行时根据缓存状态调整部分路由；ReMoE 则提前微调 router，鼓励相邻 token 复用专家，让部署时不必额外执行一套路由重排。这两类方法分别在运行时和训练时塑造复用。[4][5]

EdgeXpert 的 prefill 与它们有相似想法：允许次要路由做一点让步。但它复用的是同一 prompt、同一层中已经选过的专家，而不是依赖一个能常驻多个完整专家的缓存。

量化和剪枝更接近“让每次搬的东西变小”。EdgeMoE 包含混合精度与端侧专家管理，EdgeXpert 的比较重点是其 4-bit/2-bit 专家配置。MoE-Pruner 则利用 router 线索剪掉专家内部权重。它是细粒度非结构化剪枝，也就是保留位置不必组成规则块，需要稀疏硬件支持才能兑现收益。[6][7]

这些方法仍然要面对本文那层并集：每个候选只剩一部分权重，不代表所有候选加起来也只剩一部分。

更直接的邻居是 MoE 与推测解码的联合优化。MoE-Spec 给整棵候选树设专家预算，优先加载一份专家名单，再对名单外的路由截断或替换；它主要缩小专家级工作集。SMoLPU 已经进一步做到专家和通道两级剪枝，EdgeXpert 则继续处理通道合并读取的问题，并补上 prefill。[8][1，§II-C]

MoESD 提醒了另一个容易被忽略的条件：MoE 加推测解码并不总是吃亏。如果 GPU 上普通解码的 batch 已经激活了大量甚至全部专家，多验证几个候选所需的新增权重就可能很有限。这时推测解码仍然划算。它和 EdgeXpert 不矛盾，而是在研究不同工作点。[3]

所以，这篇论文不是重新发明“省内存的 MoE”。它补的是一个更具体的缺口：

片上存不下完整专家、候选又要一起执行时，如何把每个 token 的稀疏，变成硬件真正少读的数据。

这也是它作为微体系结构论文更完整的贡献：从路由、通道选择和误差补偿，一直设计到分组、分数汇总、地址生成和数据读取。论文定量比较的是 MoE-Pruner、EdgeMoE 和 SMoLPU，其余工作用来理解机制位置，并没有同平台横扫的证据。

9. 真要复用这套设计，还得注意什么？

9.1 软件 artifact 和硬件结果，要分两步复现

作者公开了软件 artifact，可以检查路由、合并和校准策略。但它以 bf16，也就是一种 16-bit 浮点格式运行；硬件评估用的是 A8W4。跑通软件能帮助验证算法行为，不能直接得到论文的 28nm 时延和能耗。[9]

配置也需要手工对齐。公开入口与论文有几处差异：论文树深度为 6，入口默认 --depth 为 10；Qwen3 重要性阈值在论文中为 0.80/0.55，入口默认是 0.75/0.35；默认模型路径还指向 Qwen3-30B-A3B-Instruct-2507，不能只看“Qwen3”简称就当作完全相同。

此外，路由辅助函数有把小预算选择结果补回固定 max_k 长度、并填写非零权重的逻辑。后续实际剪枝与访问是否仍满足 minor 6 个、trivial 4 个的预算，需要继续追踪，不能只根据输出张量的形状判断。代码中有预算选择，不等于实际执行已经兑现了这份预算。

9.2 最适合的是“搬比算贵”的工作点

整套设计有一条共同前提：权重搬运够贵，才值得为少搬做额外分组、评分和补算。

如果 batch 很大、计算已成瓶颈，或专家本来就能长期驻留在快内存里，交换条件就变了。同深度候选的需求差异如果特别大，合并也可能伤害质量更多。

长上下文还可能把瓶颈推到 KV cache：它保存历史 token 的 attention key/value，避免每轮重复计算。那时主要成本未必还是专家权重，不能直接套用本文结论。

量化、缓存、更好的 draft 与 EdgeXpert 有组合空间，但组合收益要重新测。更好的 draft 会改变候选树和接受长度，也会改变专家与通道需求；不是把几项加速倍数乘起来就完了。

10. 总结

EdgeXpert 抓住了一个很容易漏掉的区别：token 眼里的稀疏，和内存控制器眼里的稀疏，不一定是一回事。

单个 token 只用几个专家，整批候选却可能叫来大半个专家库；单个候选只保留少数通道，所有候选加起来又可能把权重读得差不多了。

它的两阶段设计都围绕这个问题：prefill 让次要 token 优先复用已有专家；decode 让同深度候选共同决定通道读取，再用已经加载的数据多算一点，尽量保住接受长度。最后由专用数据通路把这些选择落实到读取之前。

这里最值得带走的，不是某个剪枝比例，而是优化的目标应该放在哪里：为一个最终输出 token 搬了多少数据，花了多少额外计算，又牺牲了多少质量。

只盯着单 token 激活量，或只追求单轮少算，很容易优化了一部分，却把完整生成过程拖慢。MoE 和推测解码的组合，正好把这件事暴露得特别清楚。
