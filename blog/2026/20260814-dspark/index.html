DSpark：DeepSeek 线上跑的投机解码，为什么比纯并行 Drafter 更强

原文：DSpark: Confidence-Scheduled Speculative Decoding with Semi-Autoregressive Generation

1. 前言

做 LLM 推理优化的牛马大概都听过这句话：投机解码（Speculative Decoding）是目前少数几个在不改变模型输出分布的前提下，能真正让推理变快的方法。

但投机解码一落地，就碰上两个现实问题：

问题一：drafter 的草稿质量到底从哪里来？

最近流行的并行 drafter（parallel drafter），比如 DFlash，一次 forward 就能吐出整个 block 的 token，延迟极低。但代价是 block 内部 token 之间没有依赖——你问它”下一个 token 是什么”它还行，但要同时预测第 5、第 6、第 7 个 token，越往后越不准，acceptance rate 快速下降。

这个现象有个名字，叫 suffix decay（后缀衰减）。

问题二：高并发服务场景下，固定长度的 verification 是个浪费。

假设你的系统同时跑着 100 个用户请求，你每次都给每个请求分配 8 个 draft token 让目标模型验证。但有些请求的 draft 质量很差，第 2 个 token 就会被拒掉，后面 6 个 token 完全是白跑——这部分 KV cache 占用、验证开销，都是纯粹的浪费。

DeepSeek 这次发出来的 DSpark，就是同时解决这两个问题的工程落地方案。而且它不只是 paper，是真实部署在 DeepSeek-V4 生产服务系统上的方案，附带了线上真实流量的数据。

2. Suffix Decay：并行 Drafter 的致命伤

先说清楚这个核心问题。

投机解码的 acceptance rate 本质上是：drafter 预测的 token，和目标模型”如果自己跑会预测什么”的重合程度。

如下图，对 DFlash（蓝色，纯并行）和 DSpark（绿色）在不同 draft 位置的条件 acceptance rate 做对比：

注意看蓝色曲线（DFlash）在 Chat 任务上，第 1 个位置 acceptance rate 还不错，但到第 5、6、7 个位置就快速下跌。这就是 suffix decay。

原因很直接：并行 drafter 预测第 7 个 token 时，不知道前面 6 个 token 是什么，只能靠”盲猜”，质量当然差。

AR drafter（如 EAGLE-3）没有这个问题，因为每个 token 的预测都依赖前面的结果，但串行推理延迟高。

DSpark 的核心思路：能不能设计一种架构，既有并行 drafter 的低延迟，又有 AR 的依赖建模能力？

3. DSpark 的两个核心设计

3.1 Semi-Autoregressive 架构：并行 + 顺序的混搭

如下图，DSpark 的 drafter 由两部分组成：

  • Parallel Block（重型并行骨干）：一次 forward 并行生成整个 block 的 logit，这部分贡献主要的计算能力，延迟低
  • Sequential Head（轻量顺序头）：在并行骨干输出的基础上，用一个轻量的自回归头对 block 内的 token 依次精修，引入 token 间的顺序依赖

整个推理流程是：

  1. 目标模型跑一步，得到第一个 anchor token D
  2. 以 D 为输入，Parallel Block 并行生成 block 内所有位置的草稿 logit
  3. Sequential Head 从左到右依次过一遍，精修每个位置的预测（此时已经知道前一个 token）
  4. 同时，每个位置输出一个 confidence score（置信度）
  5. Hardware-Aware Prefix Scheduler 用这些 confidence score 决定送给目标模型验证的 token 数量
  6. 目标模型并行验证，接受前缀，拒绝后缀，开始下一轮

如下图，drafter 层数对 acceptance length 的影响：

一个浅层（2L）的 DSpark 在 Math 和 Code 任务上就已经超过了 5 层 DFlash，说明顺序依赖建模带来的质量提升，比单纯堆并行深度更有效率。

3.2 Confidence-Scheduled Verification：别把垃圾草稿送去验证

第二个设计解决”验证浪费”的问题。

DSpark 的 drafter 会为每个草稿 token 输出一个 confidence score，表示它对这个 token 预测的把握程度。Hardware-Aware Prefix Scheduler 做两件事：

  1. 按置信度剪枝：从左到右，一旦某个位置的 confidence 低于阈值，就截断，不把后面的 token 送去验证。这避免了把”明知要被拒”的 token 送进 batch。

  2. 考虑引擎负载：当系统并发请求多、GPU 内存紧张时，自动把 verification budget（每个请求验证多少个 token）调小，把省出来的算力用在更多并发请求上。反过来，并发低的时候，允许更长的 verification。

如下图，confidence threshold 的 sweep 实验：

随着 threshold 提高，acceptance rate 从 ~77%（Math）稳步上升到 92.5%，因为低质量的草稿提前被剪掉了，送进目标模型的都是”比较有把握”的 token。代价是每步平均生成的 token 数略有下降——这是个 quality vs. throughput 的 tradeoff，实际部署中根据业务场景调。

这篇论文最有说服力的部分，是 DeepSeek-V4 生产系统的真实流量数据。

如下图，throughput（系统吞吐）vs. TPS（每个用户的 token 生成速度）的 Pareto frontier：

  • 在 DeepSeek-V4-Flash 上，相同用户 TPS 下系统吞吐提升 +51%；同等系统吞吐下用户 TPS 提升 +60%

6. 个人 Take

先说结论：DSpark 是我近期看到最有意思的投机解码工作之一，原因不是方法有多花哨，而是它把两个真实系统问题解决地很干净。

suffix decay 这个问题大家都知道，但解法通常要么是”回退到 AR”（丢掉并行速度），要么是”接受质量下降”（用更长的 tree 补偿）。DSpark 用一个轻量 sequential head 在并行骨干的输出上过一遍，成本极低（主要延迟来自并行 block），却把后缀质量拉上来了。

confidence-scheduled verification 更有意思——它其实是在说：投机解码不只是一个 drafting 问题，还是一个 batch scheduling 问题。在单请求场景下，验证越长越好；但在高并发服务场景下，验证长度是要和并发请求数、GPU 内存做联合优化的。这是学术 paper 里经常忽略的系统视角。

当然，DeepSeek 有资源在自己的 V4 上直接跑线上实验，这种 privilege 不是所有研究者都有的。能从真实流量里拿到这么干净的结果，本身也是这篇工作说服力的重要来源。

感兴趣的同学可以关注一下，特别是做推理系统的，confidence-scheduled verification 那个设计应该有很多值得借鉴的地方。
