ICML’26 | DFlash：用 Diffusion 模型干掉 AR Drafter，投机解码提速 6×

原文：DFlash: Block Diffusion for Flash Speculative Decoding

1. 前言

你有没有想过，投机解码（Speculative Decoding）都火了这么久，为什么主流方案还是离不开一个小的”自回归”草稿模型（drafter）？

答案很简单——因为 AR 是天然的：预测下一个 token，一步一步来，不容易出错。

但这里有个结结实实的矛盾：AR drafter 本质上是串行的。哪怕你把它做到只有 1 层，你要草拟 16 个 token，还是得跑 16 次 forward pass。要草拟得多，drafting 的延迟就线性增长。这不就把投机解码的收益给吃掉了吗？

DFlash（ICML 2026）给出了一个非常直接的答案：把 AR drafter 换成 Diffusion 模型。Diffusion 天然支持并行生成一个 block 的 token，一次 forward pass 吐出 16 个 draft token，drafting 延迟不随生成长度增长。再配合从目标模型注入 context feature，草稿质量也不差。

最终结果：在 Qwen3 系列模型上，对比自回归 baseline 加速 超过 6×，比当时 SOTA 的 EAGLE-3（树大小 60）还快 2.5×。

2. 背景：投机解码的瓶颈在哪

投机解码的逻辑很清晰：

  1. 用一个小模型（drafter）快速草拟出 $\gamma$ 个候选 token
  2. 用大目标模型并行验证这 $\gamma$ 个 token
  3. 接受其中满足质量要求的前缀，拒绝掉的从大模型重新采样

这个框架里，验证步骤已经基本解决了——大模型本来就支持并行 prefill，$\gamma$ 个 token 塞进去一起跑不额外增加多少延迟。

真正卡脖子的是 drafting 步骤。现有 SOTA，比如 EAGLE-3，用的是一个轻量 AR 头，每次草拟一个 token，草拟 $\gamma=16$ 个 token 就得跑 16 次串行 forward。如下图，随着草拟 token 数从 4 增加到 16，EAGLE-3 的 drafting 延迟从 6ms 飙到 26ms+。

同样草拟 16 个 token，5 层的 DFlash 只需要 5ms 左右，因为整个 block 是一次并行生成的。

3. DFlash 的核心设计

3.1 用 Block Diffusion 做 Drafter

DFlash 的 drafter 是一个轻量的 block diffusion 模型。它把”生成 $\gamma$ 个 draft token”这件事转化成一个去噪过程：

  • 把 $\gamma$ 个位置初始化为 <mask> token
  • drafter 做 1 步（或少数步）去噪，输出整个 block 的 token 预测
  • 整个过程只需要 1 次 forward pass，无论 $\gamma$ 多大

这和 AR 的根本区别在于：AR 必须一个接一个地生成（后一个 token 依赖前一个），而 diffusion 在 block 内部所有位置同时预测，天然并行。

当然代价是 block 内部 token 之间没有自回归依赖，预测质量会差一些。DFlash 用下面这个设计来弥补这个缺陷。

3.2 从目标模型注入 Context Feature

这是 DFlash 里最关键的设计。

如下图，在目标模型做 prefill 的时候，DFlash 从中间若干层均匀地抽取 hidden state，把它们拼接后过一个轻量投影层，得到一个紧凑的 target context feature。这个 feature 随后被注入到 drafter 每一层的 KV cache 里。

为什么要这样做？

现有方法（比如早期的 EAGLE）也会用目标模型的 hidden state，但只是把它和 token embedding 拼在一起作为输入，随着 drafter 深度增加，这个信号会被层层淡化。DFlash 把 context feature 直接注入每一层的 KV cache，让它在整个 drafter 的计算过程中持续发挥作用，不随层数加深而衰减。

论文里专门做了 ablation（Table 9）：有 context feature conditioning 的版本比没有的，acceptance length 高出 50% 以上。

3.3 训练：Block Masking

如下图，DFlash 的训练用的是 block masking attention mask：

在一个序列里，每个 block 内的 response token 被随机 mask 掉一部分（橙色是”clean token”，绿色是”mask token”），drafter 要根据 context feature + 可见的 clean token 来预测被 mask 的位置。这个设计让 drafter 学会利用目标模型的 context 信息进行填空式预测，和推理时的行为保持一致。

4. 实验结果

4.1 主结果

如下表，在 Qwen3-4B 和 Qwen3-8B 上（thinking 模式关闭），DFlash 对比自回归 baseline 平均加速 4.9×（greedy）和 4.1×（temperature=1），同时以更小的 draft budget（block size 16）超过了 EAGLE-3（树大小 60）的 speedup。

τ（average acceptance length）达到 6.5 以上，在 Math 类任务上高达 7.87。

EAGLE-3 用树大小 60 是”尽力了”的配置，DFlash 只用 block size 16，验证开销小得多，同时 speedup 反而更高——这就是低 drafting 延迟带来的红利。

4.2 为什么 Diffusion Drafter 能超过 AR Drafter？

这里有个看起来反直觉的地方：diffusion 模型通常被认为比 AR 模型质量差（block 内部没有依赖），为什么 DFlash 的 acceptance length 反而能更高？

答案在于 drafting cost 的根本不同。

  • EAGLE-3 每次 forward 只生成 1 个 token，所以为了草拟 16 个 token 需要 16 次串行 forward，延迟高
  • DFlash 一次 forward 生成整个 block，延迟极低，可以用更多层的 drafter（更高质量）而不超过 latency budget

Table 6 里的 ablation 直接展示了这个 tradeoff：5 层 DFlash 的平均 speedup 比 1 层高出约 1.5×，而 5 层 DFlash 草拟 16 个 token 的延迟（~5ms）仍然远低于 1 层 EAGLE-3。

5. 个人 Take

这篇工作让我觉得有意思的地方，是它抓住了一个真正的系统瓶颈。

投机解码这条路上，大家一直盯着”如何提升 acceptance length”——更好的 drafter 架构、更大的 tree、更精准的 verification。但 DFlash 换了一个视角：与其纠结每个 token 预测得有多准，不如先把 drafting latency 压下去，让你有余量堆更深的模型、用更长的 block，从而在整体 speedup 上赢出来。

这其实是推理优化里一个普遍的思路：不要只优化单点指标，要看整条 pipeline 的 bottleneck 在哪。

当然局限性也有：diffusion drafter 的训练比 AR 要复杂，需要精心设计 block masking 和 context conditioning，reproduction 成本不低。另外目前结果主要在 Qwen3 系列上，在不同架构上的泛化性还需要观察。

但作为一个”用并行替换串行”的思路，DFlash 的方向是对的，值得关注。
