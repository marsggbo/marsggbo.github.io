Jev 拆解：不生成文本的 AI，究竟怎么直接做决策？

September 21, 2026 • views

2026   ·   LLM   类型化决策   概率校准   模型架构  

Jev 拆解：不生成文本的 AI，究竟怎么直接做决策？

主要资料：Jev 官方发布博客 · Jev 官方文档 · ConfTuner（NeurIPS 2025） · OpenJev · openjev-sglang · Laya · Bespoke Nimble · this-that-model

1. 一个只需要回答 A/B/C 的任务，为什么还要生成一段文字

一个客服 Agent 收到这样的请求：

信用卡被重复扣款了，希望今天退款，否则我就取消订阅。

系统接下来真正需要做的，其实是几个很具体的判断：该转给 billing 还是 account security？用户有没有明确要求退款？流失风险高不高？要不要在一小时内回复？

今天最常见的做法，是把工单、问题和候选答案一起塞给 LLM，让它返回 A/B/C 或一段 JSON。这个方案当然能用，但答案明明只有几个选项，模型还是要一个 token 一个 token 地生成；生成完还要解析 JSON、检查字段、处理越界选项，偶尔遇到 markdown code fence、解释性废话或者空字符串，还得重试。

另一头是传统分类器。BERT 接一个 Linear(H, K) 分类头，一次 forward 就能返回 K 类概率，便宜又直接；问题是 K 个类别通常在训练时已经写死。业务一旦从“billing / technical / sales”换成另一套 taxonomy，往往就要改 head、准备数据、重新训练。

Jev 想填的是两者之间这块空白：

任务和候选由自然语言在请求时定义，输出却像专用分类器一样，直接是程序可以消费的概率。

这类模型现在常被叫作 typed decision model，也就是“类型化决策模型”。这不是某一个具体模型的名字，而是一类输出合同：模型不负责自由写作，只在调用者给出的有限答案空间里做 Choice、Score 或 Boolean 判断。Jev 是闭源产品，随后出现的 OpenJev、Nimble、this-that-model、Laya 则用了完全不同的方式去实现相似能力。甚至 NeurIPS 2025 的 ConfTuner，虽然仍然保留文本生成，也在解决同一个核心问题：怎么把模型的判断变成可信、可执行的概率。

2. Jev 把自然语言理解包装成了一个概率接口

TypeSafe 在 2026 年 9 月发布 Jev，把它称为第一个 “System One model”。这个名字借用了卡尼曼的系统一/系统二：系统二慢慢推理、组织语言，系统一快速做直觉判断。这个比喻是否严谨可以另说，产品定位倒是很清楚——Decisions, not strings。

一次 Jev 请求由一份 state 和一组 questions 组成。state 是所有判断共享的当前状态，可以是字符串、JSON 或数组；每个 question 则描述“要判断什么”和“合法答案有哪些”。例如：

state = {
    "message": "信用卡被重复扣款，希望今天退款，否则取消订阅",
    "plan": "Pro",
    "duplicate_charge": True,
}

questions = {
    "department": {
        "type": "choice",
        "instructions": "哪个团队应该处理这张工单？",
        "criteria": {
            "billing": "账单、扣款和退款",
            "security": "盗刷与账户安全",
            "technical": "产品故障",
        },
    },
    "churn_risk": {
        "type": "score",
        "instructions": "评估用户流失风险",
        "criteria": ["低", "中", "高"],
    },
    "refund_requested": {
        "type": "noul",
        "instructions": "用户是否明确要求退款？",
    },
}

这三个 question 都能读到同一份 state，但彼此独立，不能读取其他问题的答案。问题 ID（上面的 department）只负责让返回结果对上字段，模型实际判断依赖的是 instructions 和 criteria，所以不能只取一个聪明的字段名，却把指令写得含糊不清。

2.1 Choice、Score 和 Noul 是 Jev 唯一能“说”的三种话

Choice 接受 2～255 个候选，返回每个候选的完整概率分布、top-1 选项和一个 confidence。候选来自本次请求，不是训练时写死的类别：今天可以判断客服队列，下一次也可以判断 Agent 该调用哪个 tool。

Score 接受 2～10 个有序等级，返回各等级的概率，再计算期望分：

\[\text{score}=\sum_{i=0}^{K-1} i\,p_i\]

假设“低、中、高”三个等级的概率分别是 [0.1, 0.6, 0.3]，期望分就是 $0\times0.1+1\times0.6+2\times0.3=1.2$。它不是粗暴地只返回“中”，而是保留了向“高”偏移的不确定性。

Noul 是 Jev 给 yes/no 判断起的名字，SDK 里也常写成 Boolean。它只需要返回一个 $P(\text{true})$，因为 $P(\text{false})=1-P(\text{true})$。

完整分布比单独返回 top-1 更有价值：

A: 0.91, B: 0.06, C: 0.03
A: 0.43, B: 0.41, C: 0.16

两次的答案都是 A，但后者几乎是掷硬币。前者可以自动执行，后者更适合追问用户、升级到更强模型或者转人工。Jev 真正卖的不是“会分类”，而是把自然语言理解变成 workflow 的控制信号。

2.2 255 个候选不够时，不是把 head 硬扩到几万个类别

官方文档给 Choice 设的上限是 255 个选项。这个数字究竟来自模型结构还是产品工程约束，官方没有解释，所以不能看到 255 就脑补成 Linear(H, 255)，更不能猜它和一个字节有关。

对于上千甚至上万个候选，官方建议把 taxonomy 做成树：先判断大类，再判断子类，并用 beam search 在每一级保留概率最高的 K 条路径。beam search 可以理解成“不只押一条路”，它会留下几个最有希望的分支继续往下搜索，避免第一层一次误判就彻底出局。

这条路线适合产品目录、工单 taxonomy 等天然有层级的任务，但它也意味着“大规模选择”不再是一次 forward：树越深，请求链越长，上一级的错误也会传给下一级。

2.3 “没有输出 token”不等于“没有计算”

Jev 当前公开的信息可以支持下面几个判断：

  • 它不向用户生成自由文本，而是返回 Choice、Score、Noul 的数值结果；
  • 多个独立 question 可以在一次请求中处理；
  • state 与全部 questions 合计最多 64k token，state 加最长单个 question 不超过 32k；
  • 官方定价是每百万输入 token 0.042 美元，输出免费，因为没有输出 token；
  • 官方宣称在自己的 workflow 中比生成式模型快 20～200 倍、便宜 40～400 倍。

最后一组数字高度依赖模型、输入长度、网络、batch 和生成长度，适合说明方向，不能当成通用 benchmark。

更重要的是，官方没有公开 backbone、参数量、attention mask、decision head 和 forward 过程。因此下面这些说法都不能当成 Jev 事实：

  • “Jev 就是让 LLM 只生成一个 A token”；
  • “它一定复用了 state 的 KV Cache”；
  • “它内部是 pointer head”；
  • “255 就是固定输出 head 的宽度”。

不生成自由文本，省掉的是自回归 decoding loop、输出传输和 parser，不是把 prefill、question encoding 和候选打分全部省掉。后面会看到，不同开源项目都对外返回相似的 JSON，底下的计算图却完全不是一回事。

2.4 RLCD 想让概率对得上现实，但 recipe 还在黑盒里

TypeSafe 把 Jev 的训练方法叫作 RLCD（Reinforcement Learning for Calibrated Decisions，面向校准决策的强化学习）。所谓 calibration，不是“模型每次都很自信”，而是它给出 0.8 的那批判断，长期看应该大约有 80% 真正答对。

这和 accuracy 是两个维度。一个模型可以 top-1 accuracy 很高，却总把 60% 的把握报成 99%；也可以 accuracy 一般，但很诚实地知道自己什么时候不会。业务要根据阈值自动退款、执行 shell command 或拦截用户时，后者往往同样重要。

遗憾的是，RLCD 目前公开的是目标，不是完整 recipe。reward 怎么算、是否真的使用 policy gradient、训练数据从哪里来、规模多大、backbone 更新哪些参数，都没有披露。Jev 可以作为闭源基线，但不能把后面任何一个开源实现的结构倒推成它的内部结构。

3. 相似的概率接口，底下至少有五条实现路线

把 Jev 的产品定义放在一边，只看“给定 state、自然语言问题和动态候选，返回概率”这件事，答案至少可以从五个地方读出来：

  • ConfTuner 继续生成文本，只是把 0～100 的 confidence token 专门校准；
  • OpenJev 在预设位置读取候选 token 的 logits；
  • Nimble 给 Qwen3.5-9B 做 LoRA，再读取单 token answer code；
  • this-that-model 从 answer slot 取 hidden state，与合法 label 对应的 LM-head weight 做点积。
  • Laya 最后连生成式 backbone 也换掉，用 bidirectional encoder 和定制 scalar head 给每个 option 打分。

这五条路线不是项目名字的简单罗列，而是一条逐步拿掉生成开销、同时逐步加深任务专用化改造的路径：ConfTuner 连生成方式都不改，只校准模型说出口的 confidence；OpenJev 拿掉 decoding loop，直接读现成 logits；Nimble 发现现成 logits 不够，又用 LoRA 专门训练；this-that-model 继续改 prompt layout，让多个 answer slot 共享一次 forward；Laya 则走到另一端，连 decoder backbone 都换成了 encoder。

这里的 logit 是 softmax 之前的原始分数，本身可正可负；softmax 把 K 个 logits 归一化后，才得到和为 1 的 K 个概率。沿着这条线往下看，会反复撞上三个问题：省掉生成之后，state 到底有没有真正复用？专门训练之后，换任务还能不能泛化？softmax 后的 0.9，又是否真的对应 90% 正确率？

4. NeurIPS’25 ConfTuner：保留文本生成，再把“说出来的置信度”调准

ConfTuner 不是 Jev-compatible server，也没有取消自回归生成，但它实现的是同一类上层能力：模型给出判断之后，再提供一个程序可以利用的 confidence。区别是 Jev 直接返回概率，ConfTuner 让普通对话 LLM 用自然语言写出 Confidence: 80%，论文把它称为 verbalized confidence，也就是“语言化置信度”。

4.1 多问模型几次，并不能得到可靠的置信度

过去常见的办法，是让模型回答同一道题很多次，用答案一致率作为 confidence：十次有九次都答 A，就记成 90%。问题是模型完全可能稳定地答错。另一些方法让 teacher model 给答案打分，也只是把 teacher 的偏差搬了过来；多次采样还会把数据构造和推理成本一起放大。

ConfTuner 的思路更直接：不为 confidence 额外造一个模糊的标签，直接用答案本身的对错训练它。答对是 1，答错是 0。困难在于，“80”和“81”在语言模型里只是普通 token，标准 token classification loss 并不知道它们在数值上相邻。

4.2 把 0～100 变成有限答案空间，再用 Brier score 训练

如下图，模型先正常生成答案，直到 Confidence: 这个位置。此时 ConfTuner 取出数字 0～100 对应的 101 个 token logits，做 softmax 得到分布 $q=(q_0,\ldots,q_{100})$。换句话说，它不只看模型最后说了“99”，还把模型对 0、1、2……100 的全部偏好都拿了出来。

如果答案正确，目标落在 100；如果答案错误，目标落在 0。训练使用 tokenized Brier score：

\[\mathcal L=\sum_{i=0}^{100}\left(q_i-\mathbb 1[i=100y]\right)^2,\qquad y\in\{0,1\}.\]

Brier score 衡量预测概率和真实结果之间的平方误差，越低越好。它属于 proper scoring rule：从长期期望看，模型如实报告自己相信的真实概率，才能把损失降到最低；无论会不会都固定报 50%，或者永远报 99%，都占不到便宜。

这个方法只用 HotpotQA 的 2000 条样本做 LoRA 微调。LoRA（Low-Rank Adaptation）不是更新整个 LLM，而是在部分线性层旁边插入很小的低秩矩阵，只训练这部分增量参数。论文设置是 rank 8、alpha 32，挂在 attention 的 Q/V projection 上。

论文报告 ConfTuner 训练约 4 分钟，推理约 1 分钟；SaySelf 因为每条输入要反复采样，训练滚到了 900 万条响应和 120 分钟。真正省下来的不是一个神奇的新 backbone，而是把 noisy proxy label 和反复采样拿掉了。

4.3 同分布校准提升明显，换任务后还是会打折

论文主要用 ECE（Expected Calibration Error，期望校准误差）衡量校准。它把样本按 confidence 分桶，再看每个桶里的平均 confidence 与真实正确率相差多少，越低越好。理想情况下，说 70% 的那一桶就应该大约答对 70%，reliability diagram 里的柱子也会贴近对角线。

在训练分布 HotpotQA 上，LLaMA 的 ECE 从 base model 的 0.4803 降到 0.0405，提升非常明显。但把同一套模型搬到 GSM8K、TriviaQA、StrategyQA 和 TruthfulQA 这些 OOD（out-of-distribution，分布外）数据集，收益会缩小。这里的 OOD 指测试任务与训练数据不来自同一分布，不是简单的“测试集没见过”。

论文还测试了 self-correction：让模型看到自己的答案和 confidence，再决定要不要修改。ConfTuner 在 HotpotQA 上把正确率变化从 base model 的 -1.2% 拉到 +3.5%，说明较可信的 confidence 确实能帮助系统决定“什么时候值得再想一次”。

这组实验给后面所有 decision model 提了个醒：把输出空间缩小，不会自动得到跨任务都可信的概率。ConfTuner 校准的是生成式 LLM 说出来的 confidence，Jev 想校准的是直接返回的分布，载体不同，distribution shift 带来的问题却一样。

不过 ConfTuner 仍然保留了完整的自回归生成：答案要生成，Confidence: 80% 也要生成。既然 workflow 最后只读取几个有限选项，下一步很自然——能不能先不训练任何新模型，直接把 decoding loop 拿掉？OpenJev 走的就是这条成本最低的改造路线。

5. OpenJev：不重新设计模型，直接读取现有 LLM 的候选 logits

“OpenJev”目前不是一个统一项目，而是一批兼容 Jev 接口的实现。它们最直接的路线，是把现成 LLM 当作打分器：prompt 里写好 state、question 和 options，跑完 prefill 后不进入完整 decoding loop，直接读取下一位置对合法答案 token 的 logits。

假设选项映射成 A、B、C。LM head 原本会为整个 vocabulary 产生几万甚至十几万个 logits，程序只取 A、B、C 三项再做 softmax。模型不用真的把 A 写进输出流，schema 外的 token 也根本没有机会成为答案。

openjev-sglang 就走这条路线：它用 Qwen3.6-35B-A3B 做 backbone，通过 SGLang 提供服务，并利用 radix cache、异步 batching 和 CUDA graph 优化 prefill。radix cache 可以理解成一棵前缀树：多个请求如果共享相同 prompt 前缀，就复用已经算过的 KV Cache，而不是从头再来。

另一个 razorback16/openjev 使用 DiffusionGemma 26B-A4B，支持 NVIDIA GPU、Apple Silicon 和图像输入，对外兼容 Jev 的 Choice、Score、Noul API。它的 confidence 使用

\[1-\frac{H(p)}{\log K}\]

计算，其中 $H(p)$ 是 Shannon entropy，分布越均匀，entropy 越高，confidence 越接近 0；分布越尖，confidence 越接近 1。这个数衡量的是“模型选得有多坚决”，不是“答案有多大概率正确”。如果模型以 99% 的概率选错，entropy confidence 仍然接近 1。

所以 OpenJev 证明的是：

  1. Jev 的 wire API 可以兼容；
  2. generation-free readout 可以套在现成 LLM 上；
  3. prefix cache 和 serving 工程可以把这条路线做得很快。

它没有证明自己复现了 Jev 的 RLCD。API compatibility、没有 decoding loop、经过专门训练和校准，是三个不同层次。

OpenJev 的优点是几乎不用动模型，短板也来自同一个地方：base model 从来没有被训练成“看一组动态 criteria，再让 A/B/C logits 表达可靠决策概率”。prompt 写法、label 顺序甚至 A/B/C 这些 token 本身的先验，都可能影响结果。于是路线继续向前一步：保留 decoder LLM，但用少量数据把它专门训练成 decision scorer。这就是 Nimble 的位置。

6. Nimble：现成 logits 不够用，就用 LoRA 专门学会做决策

Bespoke Nimble 选了一条很务实的中间路线：保留 Qwen3.5-9B 的语言理解能力，通过 LoRA 把它改造成 typed decision scorer，并且把 adapter、2676 条训练数据、324 条 held-out 数据和训练代码一起公开。

候选文本可能很长，例如“拒绝退款，因为已超过 14 天窗口”。Nimble 不直接生成这段文本，而是给每个候选分配 A、B、C 等单 token answer code，然后读取这些 code 的 logits。Python 再把 A 映射回原始字符串，所以不会出现非法 JSON。

它在 Apple Silicon 上的 ParallelScorer 会先处理共享 context，再并行给多个 field 打分；CUDA scorer 当前则会为每个 field 重新处理完整 prompt。两者 API 一样，计算成本并不一样——这也是“并行决策”必须深入到源码才能讲清楚的地方。

6.1 只做 LoRA 不稀奇，让一条事实变化时答案跟着翻转才重要

Nimble 的 contrastive data curation 会构造几乎相同的一对样本，只修改一条真正决定答案的事实。例如退款规则要求签字人必须有审批权限：

规则：只有 Mira 有权批准 account 42 的退款

原始事实：授权记录由 Mira 签署   → true
反事实：  授权记录由 Noah 签署   → false

问题、规则和其余上下文全部不变，只有关键证据变化，label 也必须翻转。这种 counterfactual（反事实）样本逼着模型关注因果证据，而不是记住“看到 refund 就答 true”之类的表面捷径。

数据 pipeline 还会分别删除两条证据，确认删掉任意一条后关键事实都应变成 unknown；再用程序把审核过的事实代入规则产生 label。最终训练集 2676 条，覆盖 10 个类别；held-out 集 324 条。label 仍然是模型审核的 synthetic label，没有人工逐条复核，这一点仓库也写得很明确。

最终训练使用 LoRA rank 16、学习率 $5\times10^{-5}$、effective batch size 8、一个 epoch，在允许的 answer code logits 上优化 cross-entropy。它没有从 Jev 蒸馏概率，也没有调 temperature 使概率与正确频率对齐。

6.2 Agreement 接近 Jev，不代表概率也一样可信

在同一批 324 条 held-out 样本上，Nimble 与 reference label 的 agreement 是 90.12%，Jev 1.13.0 是 93.21%，未经微调的 Qwen3.5-9B 是 66.36%。agreement 只看最终选择是否匹配 reference，不衡量 0.9 是否真的比 0.6 更可信。

Nimble README 反而很诚实地提醒：当前 temperature 固定为 1.0，并没有做 calibration；0.9 不代表答案长期会对 90%。此外，当前版本最多支持 26 个 enum 候选，prompt 上限 2048 token，只接受文本，多个 field 之间也不能互相依赖。

所以 Nimble 最有价值的地方不是“差 3.09 个百分点追平 Jev”，而是它把数据如何构造、adapter 怎么训练、概率从哪里读都摆到了桌面上。Jev 的 RLCD recipe 仍然闭源时，这份可复现性比一个孤立的 headline number 更值得参考。

但 Nimble 主要解决的是“怎么让 candidate logits 学会做判断”，还没有统一解决“多个问题怎样共享计算”：MLX runner 可以复用 context，当前 CUDA scorer 却会为每个 field 重跑完整 prompt。要把 typed decision 真正做成一次 forward 的原生输出，还得再改输入布局和 readout——不是每个问题各问一次，而是在同一条序列里预留多个答案位置。

7. this-that-model：再进一步，让多个 answer slot 共享一次 forward

FLock-io 的 this-that-model 用 1.88B 模型展示了另一种 readout。它不额外训练一个固定 K 类分类头，而是在每个问题后面留一个 answer slot：

Context: ...
Question 1: ... Options: (A) ... (B) ...
Answer 1: (

Question 2: ... Options: (A) ... (B) ... (C) ...
Answer 2: (
backbone 一次 forward 后，Answer: ( 最后这个位置会有一个 hidden state $h_k\in\mathbb R^H$。LM head 原本用矩阵 $W\in\mathbb R^{ V \times H}$ 把 hidden state 投影到整个词表；this-that-model 只取 A、B、C 这些合法 label token 对应的行 $w_j$：
\[p_k(j\mid x)=\operatorname{softmax}_j\left(\frac{\langle w_j,h_k\rangle}{\tau}\right).\]

假设一次有 N=3 个 question，每题最多 K=5 个候选，hidden size 为 H，那么三个 slot 先组成 [3,H]，与 label weights [5,H] 做矩阵乘法，得到 [3,5] logits。每题超过自身候选数的位置被 mask 成负无穷，再各自 softmax。

这套设计里，非法答案不是“概率很低”，而是根本不在分布的 support（样本空间）里；模型不会耗尽 token budget，也没有半截 JSON 可以解析。它还提供 state_first 和 schema_first 两种布局：前者适合同一 state 问多个问题，后者把固定 schema 放在前缀，处理一连串新 state 时可以复用 prefix cache。

不过要注意一个 causal decoder 的细节：state_first 会把多个 question 和 answer slot 依次拼在同一序列里。后面的 slot 可以看见前面 question 的文本，只是看不见“前一个问题的答案”，因为答案从未被写回序列。因此这里的“conditionally independent”更准确地说是答案之间不相互条件依赖，不等于 question 文本在 attention 上完全隔离。

7.1 它的 benchmark 很亮眼，caveat 也同样重要

仓库报告在第三方记录的 68 个问题、17 个 state 上，this-that-model accuracy 为 0.941、Brier score 为 0.042；Jev 分别是 0.765 和 0.133。Brier 越低，预测分布与真实 one-hot label 的平方距离越小。模型在 RTX 5080 laptop GPU 上的 headline latency 是 30.9ms。

但 68 条问题太小，多个 frontier model 已经 68/68 全对，根本排不出高下；图里本地电费与商业 API 定价也是两种不同成本，作者自己都强调，合理解读是一数量级差距，不是图面上的五数量级。

更大的 spatial benchmark 有 7305 个问题，公开表格比较的共同子集是 2250 条。this-that-model 得到 0.844，Jev 为 0.803，Laya 为 0.345：

这里更关键的 caveat 是：this-that-model 训练见过全部 15 种 question shape，只是没见过测试 item；其他 hosted model 则是 zero-shot。自家结果属于 in-distribution，不能据此宣布 1.9B 模型全面超过 Jev 或 GPT-5.6。

论文里另一组实验反而更有启发。模型只读取答案依赖的局部窗口时，环境从 $32\times32$ 增长到 $200\times200$，accuracy 和 latency 基本不变；把整张地图都塞进去，准确率下降，延迟则快速增长。

这说明一个经常被“大上下文”宣传掩盖的事实：decision model 不是 context 塞得越多越好，真正决定效果的是任务边界和证据选择。如果某类 decision shape 稳定，又能生成覆盖它的训练数据，小模型确实可以又快又准；一旦问题形式、输入渲染或数据分布变化，效果也可能迅速掉到 chance。

走到这里，decoder LLM 已经不生成 token，只是充当昂贵的特征提取器；LM head 也只剩几行 label weight 真正参与决策。那就会冒出最后一个问题：如果根本不要文本生成能力，为什么还一定要背着 causal decoder？Laya 给出的答案是，直接退回更适合判别任务的 bidirectional encoder，再加一个专门的 option head。

8. Laya：既然不需要生成，最后连 decoder backbone 也换掉

OpenJev 和 Nimble 的 backbone 本来都会生成文本，只是在 decision 模式下不让它生成。Laya 走得更彻底：使用 ModernBERT-large 这类 bidirectional encoder。bidirectional 的意思是每个 token 一次 forward 就能同时看左右上下文，不需要遵守 decoder LLM“只能看见前文”的 causal mask，天然适合分类和打分。

Laya 当前公开了三个 checkpoint：English 版和 typed-decisions 版使用 421M 参数的 ModernBERT-large，多语言版使用 322M 参数的 mmBERT-base。README 报告 T4 上单问题约 33ms，batch 后约 7.2ms/question；对应 context limit 分别是 512 或 1024 token。这个速度不能和一个长上下文 9B decoder 裸比，但它说明了小 encoder 在固定工作流中的吸引力。

源码把每个问题拼成下面这条序列：

[CLS] <type> instructions [SEP]
[MASK] option 0 [MASK] option 1 ... [SEP]
state [SEP]

ModernBERT 得到 shape 为 [B, L, H] 的 hidden states 后，程序取出每个 [MASK] 位置的向量。假设 batch 里有 8 个问题，每个问题最多 5 个候选，hidden size 为 H，那么 marker vectors 是 [8, 5, H]。这些向量经过一个共享的 MLP：

LayerNorm(H) → Linear(H,H) → GELU → Linear(H,1)

每个 option 得到一个 scalar logit，最后在当次的 K 个 options 上做 softmax。问题类型还会加上独立的 type embedding，让 Choice、Score、Noul 共用主体网络，却保留类型差异。

这里有个很容易被宣传语带偏的细节。Laya README 写的是多个 typed questions “in a single forward pass”，这在 API/GPU batch 层面没错；但当前 system_one() 源码会为每个 question 各自构造一条包含完整 state 的序列，再把这些序列组成 batch。四个问题意味着 state 在 token 层复制四份，并不是一份 state hidden states 分叉给四个 head。一次 batched forward 和一次 state encoding 不是一回事。

Laya 也公开了 RLCD 风格训练代码：reward 混合 log score、spherical score，对有序 Score 任务再加入 ranked probability score。这些都是 proper scoring rule。不过当前代码还会拒绝 checkpoint 中过度锐化的 temperature：仓库注释指出，某些 bucket 的温度低至 0.1006，会把 0.24 的 top probability 推到 0.99，因此运行时将温度限制在 [0.5, 5.0]，并提示受影响的 confidence 应视为未校准。这个处理很实在：比起把所有概率包装成“calibrated”，承认某个 checkpoint 的温度有问题更重要。

this-that-model 后来在自己的 spatial benchmark 上测试 laya-typed-decisions，得到 0.345，而 chance rate 是 0.343。这个数字只能说明该 checkpoint 在这组未训练过的空间任务上几乎没有迁移，不能推出 Laya 在客服路由、政策判断等训练分布内无效。反过来，Laya 自己报告的 33ms 也不能证明它在任意新任务上都又快又准。两组数字放在一起，恰好说明 decision model 的速度比较容易做，OOD 泛化没那么容易。

至此这条改造路径走到了最右端：从“照常生成，只校准 confidence”，一路走到“完全不要生成式 backbone”。改造越深，模型越像一个高效的专用决策器；代价也越明显——通用生成能力被逐步拿掉，效果越来越依赖 decision training 覆盖过的任务形状和数据分布。

9. 改造一路加深，真正的分水岭是 readout、共享计算和校准

方案 Backbone 答案如何得到 自回归生成 专门训练 当前公开程度
Jev 未公开 未公开 decision readout 对外无 RLCD，细节未公开 API、文档、部分 eval
ConfTuner LLaMA / Qwen / Ministral 生成 0～100 confidence token 有 LoRA + tokenized Brier 论文与方法
OpenJev Qwen / DiffusionGemma 候选 token logits 决策时无 通常不做专门 decision training 代码与服务
Nimble Qwen3.5-9B 单 token answer code logits 决策时无 LoRA + hard-label CE adapter、数据、recipe、代码

顺着表格从上往下，专用化程度不断增加，但这不是一张“越往下越先进”的排行榜。它更像五组工程取舍：保留多少通用能力、愿意准备多少训练数据、是否真的复用 state，以及要为 calibration 付出多少额外工作。下面四个分水岭，比项目名称本身更重要。

9.1 “不生成文本”其实有三层含义

第一层是 API 不返回自由文本；第二层是推理没有逐 token decoding loop；第三层是 backbone 本身就不具备自回归生成能力。

Nimble 和 this-that-model 满足前两层，但 Qwen 或 causal LM 本来仍然会生成；Laya 的 bidirectional encoder 连第三层也满足；ConfTuner 三层都不满足，却仍然能提供带 confidence 的决策；Jev 能确定产品层面不返回文本，内部模型属于哪一类仍未公开。

9.2 “一次并行判断”也有三种完全不同的成本

  • 把 N 条都含完整 state 的序列放进 batch，例如当前 Laya；
  • 每个问题单独 forward，但依靠 prefix KV cache 复用 state；
  • 一条序列里放 N 个 answer slot，一次 backbone forward 读出 N 个结果，例如 this-that-model。

它们都可以在 API 上写“one request”或“parallel questions”，但 token 计算量、显存和 latency scaling 并不一样。判断一个系统是否真的共享 state，不能只看返回格式，得看 prompt layout、attention mask 和 cache。

9.3 动态候选不需要固定的 Linear(H,255)

Laya 用同一个 scalar head 给 K 个 option marker 分别打分；Nimble/OpenJev 从 vocabulary 中取 K 个 label logits；this-that-model 让一个 slot 与 K 个 label weights 做点积。来 K 个候选就得到 K 个 score，参数量不随 K 改变。

但单 token label 也有代价：模型实际 readout 的是 A/B/C，候选语义必须先通过 prompt 进入 hidden state；option 很长、顺序变化或候选高度相似时，效果是否稳定需要单独测。一个漂亮的动态 API 不会自动消除模型对 prompt rendering 的敏感性。

9.4 最大的坑仍然是把“分布很尖”当成“概率可信”

至少要把四个指标分开：

  • Accuracy：top-1 选对了多少，越高越好；
  • NLL（negative log-likelihood，负对数似然）：给真实答案的概率越低，惩罚越大，越低越好；
  • Brier score：预测分布与真实结果的平方距离，越低越好；
  • ECE：不同 confidence 区间里，预测把握与真实正确率差多少，越低越好。

entropy confidence、top-1 probability 和 calibration 不是同义词。一个 99% 的错误答案对 accuracy、NLL、Brier 都很糟，却可能拥有接近 1 的 entropy confidence。真正部署时，应该在自己的业务数据上画 reliability curve、重新拟合 temperature，并分别检查新领域、新 taxonomy、新语言和不同输入格式。只在模型自己的训练分布上选一个 0.8 阈值，然后把它当成全局安全线，结结实实会踩坑。

10. 小结：Jev 真正打开的是一种模型分工方式

Jev 没有重新发明分类。它最有价值的地方，是把“state + 自然语言问题 + 动态候选 → 概率分布”做成了一个清晰的产品接口：上游负责准备状态和合法动作，下游根据概率直接执行、拒绝或升级。

但接口相似，不代表模型结构相似。ConfTuner 保留生成并校准 confidence token；OpenJev 直接读现有 LLM 的候选 logits；Nimble 用 Qwen3.5-9B + LoRA 学 answer code；this-that-model 从 answer slot 复用 LM head；Laya 最后连 decoder 都换成了 ModernBERT + option-level scalar head。实现 Jev-like 能力没有唯一架构，更没有证据说明其中哪一个还原了闭源 Jev。

“不生成文本”确实消除了 schema 外答案、半截 JSON、parser 和 decoding loop，却没有消除选错。速度也不是这条路线最难的部分：只要模型够小、输出够窄，几十毫秒并不神秘；困难的是换一个领域、换一种 state 表达、换一套候选之后，accuracy 会不会掉，0.9 还是不是真的 90%。

如果一个 workflow 节点最终只需要做决定，就没必要默认让 LLM 先写一段话。但当程序准备根据 0.9 的概率自动退款、执行命令或者拦截用户时，“这个 0.9 到底是不是真的 90%”，显然比省掉几个输出 token 更重要。

顺带扯一句题外话。这篇里几条路线，本质上都在做“预训练模型的任务专用化”：有人改 loss，有人加 LoRA，有人换 decision head，也有人直接换掉生成式 backbone。《动手学 AutoML：从 NAS 到大语言模型优化实战》里没有专门讲 Jev，但第 8、9 章讨论了 LLM 压缩、模型融合以及 LLM 驱动的 AutoML，关注的是怎么系统地寻找这类改造方案。角度不同，目标倒是很接近：不是所有任务都值得让完整大模型用同一种方式做到底。
