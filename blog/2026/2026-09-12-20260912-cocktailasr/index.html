小米 CocktailASR-1：一个模型搞定”鸡尾酒会问题”，还能选择性装聋

原文：Xiaomi-CocktailASR-1 Technical Report 代码：xiaomi-research/xiaomi-cocktailasr-1（模型权重与推理代码在 HuggingFace: Ease3/Xiaomi-CocktailASR-1）

1. 前言吐槽

你有没有想过，为什么现在一堆语音大模型（Qwen3-ASR、StepAudio、甚至 Gemini）在安静环境下转录得又快又准，可一旦录音里有两三个人同时说话，识别结果就直接崩掉？这就是语音圈子里说了几十年的鸡尾酒会问题（cocktail party problem）：人耳能轻松地在嘈杂人声中锁定你想听的那个人，机器却做不到。

这次拿到手的这篇技术报告——Xiaomi-CocktailASR-1——就是冲着这个问题来的。作为研究AI方向的牛马，我看到”目标说话人语音识别”（Target-Speaker ASR，简称 TS-ASR）这个方向已经不是第一次了，但这篇论文里有两个点让我觉得值得写一写：一是它用一个纯 LLM 架构同时把”多人识别、单人识别、拒识、思维链”四件事全揽了，二是它把代码和权重都放出来了，可以直接拿来验证。今天就结合论文和开源的 modeling 代码 聊聊它到底怎么做的。

2. 现有方案的核心矛盾

先说清楚 TS-ASR 这个赛道原来是怎么玩的。主流做法基本分两派：

  • 端到端 + speaker embedding：先用一个说话人编码器（比如 d-vector / x-vector）把参考语音编码成一个定长向量，再把这个向量注入到 ASR 模型的某一层，让模型”记住”该关注谁。
  • 显式语音分离 + ASR 级联：先用语音分离模型把混合音频拆成多路单人语音，再对目标那一路跑普通 ASR。

这两种做法都有一个绕不开的坑：一旦专门为多说话人场景做了优化，单说话人场景的识别效果就会掉一截——因为说话人编码器/分离模块引入的噪声和信息损失，在没有干扰说话人的时候反而成了负担。而且更麻烦的是，这些方法基本都没有”拒识”能力：如果参考说话人根本没出现在这段音频里，模型也会强行给你吐出一段文本，而不是老老实实说”没有这个人”。

这也是整个 TS-ASR 行业的核心矛盾：多说话人抗干扰能力和单说话人保真度，鱼与熊掌不可兼得。CocktailASR-1 的目标就是同时啃下这四件事：多人识别 SOTA、单人识别不掉分、负样本能拒识、还要能给可解释的推理过程。如下图，这四个能力被放在一个统一框架里同时实现。

3. 整体架构：不做分离，直接把参考语音当 prompt

CocktailASR-1 的架构说白了非常”LLM 化”——没有独立的说话人编码器，也没有语音分离模块，架构如下图：

三个组件：

  1. Audio Encoder：基于 Data2Vec2（D2V2）的自监督语音编码器，参数量 0.6B，用 FBank 特征作为输入,把语音转成 1280 维的帧级表征。这里有个关键设计：它没有单独套一个说话人识别（SV）模型去抽取声纹向量，而是让 D2V2 本身在语义信息之外自然地把说话人信息也编码进同一套帧级表征里——相当于省掉了传统方案里”额外接一个 speaker encoder”这一步。
  2. Linear Adapter：一个轻量线性层，把 D2V2 输出的维度对齐到 LLM 的输入维度，做跨模态桥接，没有花里胡哏的结构。
  3. LLM 主干：Qwen3-8B，负责最终的文本解码生成。

最有意思的是输入的组织方式：把参考语音也编码成帧级 embedding，和目标语音拼在一起，一起喂给同一个音频编码器和 LLM，而不是先把参考语音单独编码成一个定长声纹向量再注入。这个设计直接解决了前面说的矛盾——因为参考语音和待识别语音走的是完全同一套编码路径，没有额外引入信息损失的瓶颈层,所以单说话人场景下的表现才能保持和普通 ASR 模型接近。

4. 输入怎么拼？结合代码看细节

论文里说输入是”参考语音 + 待识别语音”的拼接，但具体怎么拼、拼接细节里藏着不少工程 tricks。这部分开源仓库里没有代码文件（xiaomi-research/xiaomi-cocktailasr-1 这个 repo 只放了 README 和一个批量推理脚本），真正的模型定义在 HuggingFace 的 Ease3/Xiaomi-CocktailASR-1 上，通过 trust_remote_code 加载，核心逻辑在 feature_extraction_mic_asr.py 的 prepare_audio 里。

拼接的顺序是：

[参考语音] + [1秒静音] + [待识别语音]

中间插入 1 秒静音不是随手为之，而是显式地把参考段和待识别段隔开，让模型（以及后面 CoT 里要输出的”0-3.14s 是 enrollment speech，3.14-4.14s 是静音”这种时间戳描述）能够清楚地区分两段的边界。

参考语音的长度处理也有讲究：

  • 太短（≤ 某个最小阈值）：随机生成一个 1-4 秒范围内的目标长度，用零填充凑够长度；
  • 太长（超过最大阈值）：同样在 1-4 秒范围内随机采样一个目标长度，然后从原音频里随机截取一段（而不是固定截头或截尾）；
  • 长度正好：原样使用。

再加上响度层面的 peak normalize（把音频峰值统一标准化到 0.99），保证输入分布稳定。这一套”随机时长 + 随机起点裁剪”的策略,本质上是在做数据增强：训练时模型见过的参考语音长度和位置都是随机的,这样才能保证推理时无论你喂进去几秒的参考音频，模型都不会因为”没见过这种长度”而翻车。

高层的调用接口非常简洁，直接体现在开源的批量推理脚本 tools/test_batch_scp.py 里：

from transformers import AutoModel

model = AutoModel.from_pretrained(
    "Ease3/Xiaomi-CocktailASR-1", trust_remote_code=True, torch_dtype="bfloat16"
).cuda().eval()

text = model("target.wav", "ref_speaker.wav")   # 拼接逻辑在模型内部自动完成

也就是说，用户侧完全不需要关心”参考音频怎么和目标音频拼起来”——model(wav, ref) 这一层调用直接封装了 prepare_audio 的拼接细节，输入可以是文件路径、numpy.ndarray 或 torch.Tensor，非 16k 采样率的音频会自动重采样。这个封装做得挺克制的，没有为了”看起来通用”而过度设计一堆参数。

5. 训练怎么分阶段：从纯 ASR 一路”加码”到 TS-ASR + CoT

CocktailASR-1 没有想着一步到位直接训练最终形态，而是用了一个四阶段的课程学习（curriculum）式 pipeline：

  • Stage 1（ASR Base）：不带参考语音，用标准 ASR 的 prompt 在普通单说话人数据上训练，目的是先把音频编码器和 LLM 的语言建模能力打好底子。
  • Stage 2（TS-ASR Base）：正式引入参考语音+目标语音的拼接范式，训练数据里混入约 50% 概率的噪声/干扰说话人混合策略，同时掺入少量负样本（参考说话人不在目标音频里的样本），让模型初步具备”认人”和”拒识”的雏形。
  • Stage 3（TS-ASR + CoT）：加入思维链数据，和原始 TS-ASR 数据按等比例混合联合训练，让模型学会先”推理”再”回答”。
  • Stage 4（TS-ASR Fine-tuning）：在高质量数据上做 SFT，再叠加强化学习（RL）做进一步优化。

这种”先学会听清楚 → 再学会认人 → 再学会说明理由 → 最后精调”的顺序，本质上还是在缓解第 2 节说的那个核心矛盾：如果一开始就把多说话人干扰、拒识、CoT 一股脑塞进训练，模型很容易在”保真度”和”抗干扰”之间找不到平衡点；分阶段递进给了模型一个从易到难消化的路径。

训练数据规模也交代得比较清楚：多说话人混合数据约 40 万小时（来自 AMI/AliMeeting/LibriMix 等开源数据加模拟混合与真实对话场景）,单说话人数据约 60 万小时（参考语音和目标语音来自同一说话人的不同录音）,负样本约 1 万小时。这个数据规模量级，说明这不是一个”小模型 demo”，而是实打实想把 TS-ASR 做到工业可用水平的工程。

6. 拒识能力怎么训出来的：不是加阈值,是让模型学会说”没有”

传统方案想做”拒识”，大概率是在说话人相似度上加一个后处理阈值——算一个 cosine similarity，低于某个值就判定为不存在，然后手动清空输出。这种做法的问题是阈值很难跨数据集泛化，而且是模型外挂的逻辑，不是模型自身的能力。

CocktailASR-1 的做法是把”拒识”直接变成一种训练目标：负样本（参考说话人缺失）在训练数据里从 Stage 2 开始出现，并且在后续阶段逐步提高负样本比例，让模型直接学会在这种输入模式下把 <answer> 标签内的内容输出为空，而不是依赖推理时的外部阈值判断。

效果也体现在实验里（第 7 节会细讲）：Qwen3-ASR 和 StepAudio2 这类没有专门做拒识训练的模型,遇到负样本时拒识率是 0%——它们会一本正经地把不存在的说话人的话”编”出来；而 Gemini 虽然也有一定拒识倾向,但代价是在正样本（说话人确实存在）场景下误拒率高达 21.31%，也就是经常把明明存在的目标说话人误判为不存在。CocktailASR-1 则是在保持误拒率极低（LibriSpeech 上只有 0.36%）的同时，拒识率做到了 79.59%——这才是”该拒的时候拒，不该拒的时候别乱拒”的平衡感。

7. Chain-of-Thought：让模型把”为什么选这个人”说出来

CoT 这部分是我觉得整篇论文最有意思的设计。看下面这张图里的三个例子（单说话人、双说话人混合、负样本）：

CoT 的推理内容不是那种”让模型自由发挥碎碎念”的开放式思维链，而是有明确的结构化步骤：

  1. 音频信息：明确切分参考语音段、静音段、待识别语音段各自的时间戳；
  2. 参考语音信息：判断参考说话人的性别；
  3. 每个候选说话人信息：判断混合音频里出现了几个人，每个人的性别，以及每个人与参考语音的声纹相似度打分；
  4. 目标说话人判定：比较各候选人与参考语音的相似度，选出得分最高的那个；如果最高分低于阈值（论文中用的判定标准是相似度 < 3 判定为目标说话人缺失），则判定为负样本，输出为空。

这个相似度打分不是模型凑数瞎编的，而是训练数据构造阶段就用 CAM++ 声纹模型算好的真实相似度，把 0-1 的连续相似度分数离散映射到 1-5 的等级上，作为 CoT 监督信号的一部分写进训练样本里。也就是说，模型是在学习”模仿一个真实声纹相似度计算过程”的推理模式，而不是学一套自己编的、缺乏客观标准的托词。

从数值上看，CoT 带来的提升是存在但比较轻微的：LibriMix 2mix 上从 4.11% 降到 3.87%，LibriMix 3mix 上几乎没变化（12.287% → 12.285%）。

我的理解是，CoT 在这里更大的价值不是”提升识别精度”，而是提供可解释性——尤其是拒识场景下，用户能看到模型到底是基于什么相似度判断认为”这个人不在”，而不是一个黑盒的空字符串。这对实际落地（比如会议纪要、客服质检场景需要审计判断依据）是有意义的。

真实场景难度明显更高（21%-20% 区间的 WER，比合成数据的个位数百分比要高不少），这也符合直觉——真实录音里混响、远场拾音、说话人重叠模式都比模拟数据复杂得多。但相对已有的专门做 TS-ASR 的 SOTA 方法（SQ-Whisper、MC-TS-ASR），CocktailASR-1 依然是全面领先。

可以看到 CocktailASR-1 在单说话人场景下的 WER 和专门做单人 ASR 的 Qwen3-ASR、StepAudio2 基本处于同一水平线（LibriSpeech 上 1.73% vs 1.87%/1.58%），甚至在 AMI-ihm 这种远场场景上大幅领先（8.89% vs StepAudio2 的 37.54%）。同时误拒率（FRR）控制得很低，说明”给模型加拒识能力”这件事没有拖累它在正常场景下的表现。

9. 一点 take

整体看下来，CocktailASR-1 给我的感觉是,它没有在架构上搞什么花活,核心创新其实是工程和数据层面的取舍：用自监督编码器自带的说话人信息取代独立声纹模块、用”参考+静音+目标”这种统一拼接范式取代显式分离、用课程学习式的四阶段训练去平衡多人/单人/拒识这三者的冲突,再用结构化 CoT（而不是自由生成的思维链）把声纹相似度判断过程显式化。这几个设计单独看都不算多新颖，但组合在一起、并且真的把权重和推理代码开源出来让人能跑起来验证,这一点还是值得说一句实诚。

如果你想验证效果,Ease3/Xiaomi-CocktailASR-1 这个 HF 仓库直接 trust_remote_code=True 就能加载,tools/test_batch_scp.py 也给了现成的批量测试脚手架,想接自己的多说话人场景数据做个 baseline 测试成本不算高。

如果这篇文章涉及的语音多模态架构设计、SSL 编码器与 LLM 的 adapter 对齐方式你想系统深入,可以看看我之前出版的《动手学 AutoML：从 NAS 到大语言模型优化实战》，书里 LLM 效率优化和多模态适配那部分内容,和本文讲的 encoder-adapter-LLM 三段式架构设计思路有一定的呼应。
