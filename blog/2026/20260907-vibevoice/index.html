1. 实时会议转写，难点不只在“听清”

想象一个会议助手正在听两个人说话。它每隔几秒给出一段文字，文字本身并不难理解；难的是它要在此刻就交出去：

Speaker 0: 我们先看延迟。
Speaker 1: 好，我把结果发出来。

后面 Speaker 0 再次开口，系统必须还叫他 Speaker 0。如果到整段录音结束后才发现前面的编号弄反了，再回头改历史记录，那当然可以提高最终稿质量，但对实时 agent 没什么帮助：agent 在第一次看到那句话时就已经据此做了决定。

这也是这篇 VibeVoice-ASR-Streaming 真正想解决的约束。它不是单纯的 streaming ASR（Automatic Speech Recognition，自动语音识别），而是 streaming speaker-attributed ASR：在音频还在到达时，持续输出“谁说了什么”，并在输出时就固定说话人归属。

论文里的 speaker attribution 不是“这位是张三、那位是李四”的实名身份识别；它只是在同一场会话内按首次出现顺序分配 Speaker 0、Speaker 1，之后保持编号一致。也就是说，它不需要预先注册一段张三的声纹，重点是 online diarization（在线说话人分段与归属）和转写能否一起稳定下来。

传统方案通常是两条流水线：ASR 先给文字，diarization 再抽说话人 embedding、建一个 speaker cache（缓存已经出现过的人）、把每段话聚成同一个人。拆开并没有错，但实时场景里会遇到两个实际问题：

  1. 只看当前两秒音频，句子可能刚好在块边界断开，甚至还没来得及听到对方接话；
  2. 当前声音该匹配哪个历史说话人，仍要依赖另一个状态机或聚类器，后续还可能改标签。

VibeVoice 的选择是把这两件事放进同一个 LLM（large language model，大语言模型）自回归模型：历史音频、历史文本、当前音频依次排在同一条上下文里。它不声称“切块没有代价”，论文反而专门量化了代价；它的核心主张是，把有限未来和无限但昂贵的历史以不同方式留住，才能在低延迟下把“词”和“人”一起交付。

2. 关键不是分块，而是让下一块接着上一块说

最直觉的 streaming 做法是：每 2 秒裁一段音频，各跑一次 ASR。这样吞吐很舒服，但每段都是孤岛。

比如 0-2 秒里说“那个方案”，2-4 秒才说“我觉得不太行”；后一段不知道“那个方案”指什么。对多人会议更麻烦：第 0 段第一次出现的声音被临时叫作 Speaker 0，第 15 段同一个人回来，独立 ASR 根本没有理由继续用同一个编号。

论文把第 (k) 个语音块记为 (X_k)，它对应的带说话人文本记为 (Y_k)。模型实际看到的不是一批相互独立的 (X_k)，而是一条交错序列：

提示词, X0, Y0, X1, Y1, X2, Y2, ...

于是生成 (Y_k) 时，条件里同时有三类东西：

[ p(Y_k \mid X_{<k}, \widetilde{X}k, Y{<k}) ]

  • (X_{<k})：此前听过的音频；
  • (Y_{<k})：此前已经写出的文本和 Speaker 编号；
  • (\widetilde{X}_k)：当前要交付的块，加上一小段未来音频。

这条式子不需要死背，它只是把设计动机写明白：历史 (X_{<k},Y_{<k}) 用于延续会话状态，当前块后的那一点 (\widetilde{X}_k) 用于避免在边界处过早拍板。 如果把历史扔掉，再额外维护声纹库或聚类器，本质上只是把同一份状态搬到了模型外面。

论文的整体图已经把这件事画出来了。注意蓝色的连续音频 latent 和橙色的文本 token 是交替进入同一个 LLM 的，不是“音频模型出一份结果，再交给语言模型润色”。

3. LLM 到底听到了什么：一帧不是一个字，也不是原始波形

先看音频怎样变成 LLM 能吃的输入。VibeVoice 没把 24 kHz 原始波形直接塞进 Qwen2.5，而是冻结了两个预训练 encoder：

  • Acoustic tokenizer 提供频谱、音色、韵律等声学细节。这些是区分两个嗓音、感知重叠和停顿需要的信息。
  • Semantic tokenizer 提供更贴近语音内容的确定性特征。可以把它理解成给 LLM 一条更容易对齐文字的提示线索。

二者在时间上对齐，拼接后投影到 Qwen2.5 的 embedding 空间，也就是 LLM 内部用于表示一个输入位置的向量。由于波形累计下采样了 3200 倍，24 kHz 输入每 (3200/24000=133.3) ms 得到一帧 latent（压缩后的连续语音表示），也就是每秒 7.5 帧。后面所有“15 帧”“22 帧”“4 帧”都是这个时间粒度，而不是某种神秘超参数：

配置 新增音频 额外前瞻 一次送入模型的窗口
15-frame 2.0 s 4 帧，约 0.53 s 约 2.53 s
22-frame 约 2.93 s 4 帧，约 0.53 s 约 3.47 s

这也解释了为什么仓库的服务代码强调要从 checkpoint 的 preprocessor_config.json 读取 chunk_frames 和 lookahead_frames，不能随手把 15-frame 模型按 22-frame 的节奏喂。模型训练时学到的就是某一种“窗口长度、输出边界、前瞻”的联合契约，形状不报错不等于语义没变。

4. Look-ahead：不是为了看更多，而是为了少在边界处猜

如果模型要给 0.0-2.93 s 的声音生成文字，为什么还要等 2.93-3.47 s 的半秒？这段音频不属于当前输出，等它不是平白增加延迟吗？

先看一个实际的边界：有人在块末尾发出“我觉得这个方案……”，接下来半秒里可能接“可以”、可能接“不行”，也可能说话人换了。对整句文字、断句位置和 speaker label 而言，边界右侧的证据很有价值。没有它，模型只能把当前块末尾当作真实停顿，或者过早认定最后几个音节属于谁。

所以 look-ahead 的含义不是“把未来的文字提前输出”，而是在提交当前块之前，允许模型看过边界右侧一点点声音。那半秒在下一轮会原封不动地作为下一块的正式输入，再生成它自己的文字。窗口之间因而有重叠，时间轴却只以前面的 chunk 长度推进。

下面这张图把一次 turn 展开。发布的 22-frame 版本每轮负责约 2.9 秒新音频，再附约 0.5 秒前瞻；服务端从 buffer 中切出 3.4 秒窗口，却只从 buffer 弹出前 2.9 秒，末尾 0.5 秒留给下一轮。

论文报告的 22-frame 配置，期望的说话人归属延迟是：

[ \frac{C}{2}+T_{\text{lookahead}} =\frac{2.93}{2}+0.53\approx2.00\text{ s} ]

这里的 (C/2) 不是系统计算耗时，而是假设一个词均匀落在 chunk 内，它平均要等到当前 chunk 结束才会被交付的时间。再加 0.53 秒前瞻，就得到稳态下的算法期望延迟。15-frame 配置相应为 1.53 秒。

另一个容易被宣传数字掩盖的点是：首包延迟更大。 第一段没有历史块可先行输出，必须等完整 chunk 和前瞻都到齐。因而 22-frame 是约 3.47 秒，论文按帧报告为 3.5 秒；15-frame 是约 2.53 秒，报告为 2.5 秒。2.00 秒不是用户说完第一句话两秒后就一定看见结果，而是流稳定之后，对 chunk 内一个平均位置词的度量。

前瞻到底值不值得等？论文在固定 22-frame、7B 下测试 (L=0,2,4)。每增加 2 帧，期望延迟固定多 0.267 秒；五套评测的平均 WER/CER（词错误率/字错误率，都是越低越好）从 27.18 降至 25.91、再到 24.66，带 speaker 归属的 cpWER/cpCER 从 35.88 降至 34.09、再到 31.55。

cpWER/cpCER 可以理解成“按每个人把他说过的话拼起来，再在说话人编号的所有匹配方式中取最小错误”。它同时惩罚听错字词和把话挂错人，因此比普通 WER/CER 更接近这篇论文要解决的问题。最后两帧对 cp 指标还带来 2.54 个点改善，超过对普通识别指标的 1.24 个点改善，说明右侧上下文在说话人归属上尤其有用。

这不是证明“0.5 秒对所有会议 ASR 都最优”。它只说明在本文数据、22-frame、7B 的设定下，作者没有观察到 4 帧处已经饱和；更小前瞻换更低延迟是一个合理但可量化的取舍。

5. Speaker 0 为什么不会每两秒失忆

上一节的 look-ahead 解决“边界后发生了什么”，但它本身不能解决“这是谁”。Speaker 0 的一致性来自交错上下文中的历史文本：模型已经在 (Y_0) 中输出过 Speaker 0:，后面处理 (X_{12}) 时仍能读到这个编号以及那个人此前说过的内容和声音。

这和只用声纹 embedding 做在线聚类的差别在于，模型可以同时用三类证据：

  • 声学线索：声音是否像此前的人；
  • 语言线索：这句话的措辞、口音和前后话题是否连续；
  • 对话线索：刚被提问的人是否合理地接话，上一轮是谁在说。

当然，这不表示 LLM 学会了可靠的现实身份识别，也不表示它永远不会把相近的嗓音混掉。它只是把“归属”建模成同一条生成序列里的预测，而不是在转写之后再接一个独立的聚类阶段。

论文还有一个很好的小实验。发布版本把 Speaker k: 放在片段文字前面，让 UI 在第一个文字 token 就知道是谁在说；另一个版本故意放在片段末尾，让模型多听一会再报身份。若 attribution 纯粹依赖声纹，后者理应更准，因为它能拿到更长的语音。但五套平均 cpWER/cpCER 几乎相同，31.55 对 31.56；普通 WER/CER 上尾置标签反而高 0.98 个点。

这组结果至少支持一个较克制的判断：在这套端到端模型和约 2-3 秒窗口里，模型已经能利用足够的声学、文本和对话证据决定标签，因此没有显示出“必须等到片段说完才更准”的收益。它不等价于说传统 speaker embedding 没用，更不等价于长重叠语音已经解决了。论文自己也承认，多人长时间同时说话时，单一文本流必须把重叠语音串行化，表现会下降。

6. 它怎么学会在块边界停下：训练目标里有一个明确的交接符

仅在推理时切音频不够。模型若在训练中始终看完整录音，推理时突然要求它每 2.93 秒就交一份局部转写，它很可能在块中间断句、把文字分配到不该属于它的块，或者不知道何时把控制权还给音频输入。

作者的训练路线因此分三步，但模型主干和自回归目标并没有反复换：

  1. 离线 speaker-attributed 训练：先完整看到录音，学会多说话人的“谁说了什么”。
  2. streaming pre-training：从同尺度的离线 checkpoint 出发，把样本改写成 X0,Y0,X1,Y1,...，每个 (X_k) 带固定前瞻。论文使用约 42 万小时中英文语音，让这种格式成为模型的默认工作方式。
  3. streaming fine-tuning：再用约 1.3 万小时精选的公开与合成数据收尾，着重压实用户会感知的行为，例如转写书写规范、编号一致性和热词遵循。

训练样本也不是简单按字符切文本。作者先用 Qwen3-ForcedAligner-0.6B 得到词级时间，对每个 chunk 按词的结束时间分配目标文本；末尾落在边界前 0.1 秒容差内的词归当前块。合成多人数据里还加入了专业术语、数字的自然口语读法与规范书写的差异、多人 overlap 和 room impulse response（模拟房间混响与麦克风响应）。这一步的意义是让“每个块应该交什么文本”变成有时间对齐的监督，而不是让模型凭字符长度猜边界。

每个 (Y_k) 的末尾都监督一个 <|text_chunk_end|> 特殊 token，即使这一块是静音、文字为空也一样。它相当于模型和音频流之间的交接符：模型生成到它，就说明“本块输出结束，可以追加下一块音频了”。输出长度没有预先给定，何时结束仍是模型要学会的预测。

7. 从源码看，真正的 streaming 状态在哪里

论文图很干净，但工程上至少要保存两份状态：语义上的会话历史，以及让历史不被每轮重新计算的 KV Cache。KV Cache 是 Transformer 对已处理 token 的 key/value 中间结果缓存；没有它，第 (k) 块都重算前 (k-1) 块，单会话成本会随时长接近平方增长。

先看 Hugging Face 参考路径。streaming_generate 先从完整音频构造重叠 feature windows；随后每一轮把新的音频 embedding 追加到 past_key_values，自回归生成当前文字，最后无条件把块结束 token 也写回缓存。下面保留默认 temperature=0 时的 greedy decoding 主线，省略了可选的采样与 repetition penalty 分支。

# vibevoice/modular/modeling_vibevoice_asr.py
# class VibeVoiceASRForConditionalGeneration
# def streaming_generate(...)，约第 529 行
for chunk_idx, feat_chunk in enumerate(feature_chunks):
    audio_embeds = torch.cat([sp_start_embed, feat_chunk, sp_end_embed], dim=1)
    outputs = self(inputs_embeds=audio_embeds,
                   past_key_values=past_key_values, use_cache=True,
                   return_dict=True)
    past_key_values = outputs.past_key_values
    next_logits = outputs.logits[:, -1:, :]

    chunk_tokens = []
    for _ in range(max_new_tokens_per_chunk):
        next_token_id = torch.argmax(next_logits[:, -1, :], dim=-1).item()
        if next_token_id == text_chunk_end_id or next_token_id == eos_id:
            break
        chunk_tokens.append(next_token_id)
        next_embed = embed_tokens(torch.tensor([[next_token_id]], device=device))
        outputs = self(inputs_embeds=next_embed,
                       past_key_values=past_key_values, use_cache=True,
                       return_dict=True)
        past_key_values = outputs.past_key_values
        next_logits = outputs.logits

    tce_embed = embed_tokens(torch.tensor([[text_chunk_end_id]], device=device))
    outputs = self(inputs_embeds=tce_embed,
                   past_key_values=past_key_values, use_cache=True,
                   return_dict=True)
    past_key_values = outputs.past_key_values
    yield chunk_idx, total_chunks, tokenizer.decode(chunk_tokens, skip_special_tokens=True)

这段的输入 feat_chunk 是一个窗口的 audio latent，past_key_values 则是提示词和所有历史音频/文本的缓存。输出不是整篇最终转写，而是 generator 每轮 yield 一条 chunk 文本；更新后的 past_key_values 留给下一个 feat_chunk。最关键的不是 yield，而是最后仍把 text_chunk_end_id 写回缓存，否则下一轮上下文和训练格式就错了一格。

实时服务又多一个工程矛盾：vLLM 的公开接口不是“把我手上的 KV Cache 原样拿回来继续 append”，而是一次 request 接一次 request。仓库的解法是每轮重建“到目前为止”的 token prompt，但打开 automatic prefix caching（前缀缓存）；旧前缀的 token 和音频窗口保持完全一致，就能命中缓存，不会重新 prefill。

# vllm_plugin/asr_streaming_server.py
# class StreamingSession
# async def push(self, window)，约第 275 行
self._windows.append(window)
tokens = self._tokens + [self.audio_token_id]
k = len(self._windows) - 1

# 已处理的窗口只传 None；uuid 不能变，vLLM 才能确认它们是同一前缀。
uuids = [f"{self.session_id}-{i}" for i in range(k + 1)]
audio = [None] * k + [window]
out = await self.engine.generate(tokens, audio, uuids,
                                 self.sampling_params, req_id)

gen = list(out.outputs[0].token_ids)
while gen and gen[-1] == self.text_chunk_end_id:
    gen.pop()

# stop token 虽不回显，仍必须手动补进下轮前缀。
self._tokens = tokens + gen + [self.text_chunk_end_id]
return _strip_specials(out.outputs[0].text)

这段代码里有三个很实在的点。

第一，旧窗口在 audio 数组里是 None，所以网络载荷不会随着会话变长不断复制旧波形；但 UUID 必须字节级稳定，否则 vLLM 无法把“第 3 个音频窗口”当成原来的对象，缓存哈希会失效。第二，文本 prompt 仍然包含全部历史，因为它既是说话人编号的记忆，也是 LLM 的条件；省掉的只是重新计算，不是语义上的历史。第三，服务端一旦发现多模态处理缓存被驱逐，就会降级为重发所有窗口，这比悄悄把历史音频当作不存在更可靠，但也说明部署侧要给 mm_processor_cache_gb 留够空间。

WebSocket 路径也和图一致：当缓冲区长度达到 window_samples 时，服务端送 buf[:window_samples] 做一次推理，然后执行 buf = buf[chunk_samples:]，只消费 chunk，不消费 look-ahead。最后一个不够完整的窗口会补零，避免短音频编码时多出一帧、同时又缺少前瞻，偏离训练分布。

8. 实验要读出什么，也要知道它没有证明什么

论文把英语按 WER、中文/日文/韩文按 CER 计分，二者都是编辑距离除以参考文本长度，越低越好。22-frame 7B 在四个会议集加 MLC-Challenge 的五集平均普通识别误差为 24.66；论文对比的 Gemini 3.5 Transcribe Live 为 25.23，其余三项线上服务更高。speaker-attributed 评测中，论文报告该配置在 13 个可比较设置中有 12 个达到最好或并列最好。

下图中更值得注意的并不只是粗体数字，而是 Google STT 的两列：D0 是第一次发出时的标签，Dfin 是整段录音处理后回写修订的标签。二者的文本相同，差别只在说话人归属。这个对照恰好说明了论文的任务定义：它看重的是先交付的标签能否成立，而不是事后把标签改漂亮。

不过延迟对比要谨慎读。VibeVoice 报的 2.00 秒是上面解释过的期望算法延迟；Azure CT 的 8.21 秒和 Google STT 的 9.12 秒是作者在其服务上测得的 wall-clock 平均值，计量口径并不完全相同。论文还报告 Google 的文字约 1.5 秒就稳定，但 speaker label 会在后续 16.5-31.3 秒继续修改。这个观察很有意思，却不足以推出“所有实际部署都比这些服务快很多”。

更诚实的一张表是作者将 streaming-7B 和其初始化来源的非流式 VibeVoice-ASR 放在同一评测下比较。变成流式后，普通 WER/CER 在五套数据上增加 0.75-3.53 个点，cpWER/cpCER 增加 5.13-6.67 个点；后者掉得更明显，符合“有限未来上下文对说话人归属更伤”的直觉。

性能方面，论文只测了一个具体 serving 点：7B、15-frame、batch size 1、A100 80GB PCIe、bfloat16 和 vLLM。30-480 秒音频上每个 2 秒 chunk 的 decode 为 146-208 ms，RTF（real-time factor，即处理耗时除以音频时长，低于 1 才跟得上实时音频）为 0.073-0.104。它说明该配置的模型 decode 留有余量，但不包含浏览器采集、排队、网络和音频解码的完整端到端服务延迟。

最后还有几个边界条件不能跳过：训练语言受词级 forced aligner 覆盖限制，目前是十种语言；发布 checkpoint 面向最多约 8 分钟录音，因为未压缩上下文会线性涨计算量；多人长时间重叠仍困难；并且短单人音频不是这个模型的强项。把这些限制和上面的主结果放在一起看，才比较接近它实际能做什么。

9. 小结：把两种“上下文”放在了该在的位置

VibeVoice-ASR-Streaming 的思路并不玄：

  • 用历史音频与历史文本，让会话中的 Speaker 编号和语义不断延续；
  • 用固定 4 帧前瞻，减少块边界处的词和说话人误判；
  • 用 <|text_chunk_end|> 把每轮生成变成可学习、可服务化的交接协议；
  • 用 KV Cache 或 vLLM 的 prefix cache，避免这种“保留历史”的正确做法在计算上变成灾难。

这篇报告比较有价值的地方，在于它把算法契约、训练样本构造、在线窗口缓存和部署实现都公开了，也明确给出了流式化损失的量级。对想做会议 agent 的人，最直接的启发不是“换一个 7B ASR 就好了”，而是先问清楚自己的产品需要哪一种稳定性：文字稳定、说话人标签稳定，还是两者都要在几秒内稳定。它们对应的延迟预算和系统状态，确实不是一回事。

顺带一提，ASR streaming 和《动手学 AutoML：从 NAS 到大语言模型优化实战》讲的 NAS、压缩并不直接重合；但两者有一个很像的工程问题：模型效果不是只看单次 forward，输入格式、上下文长度和部署资源都会变成设计的一部分。书里把 LLM 架构自动化、压缩和后训练剪枝整理成了可复现的实现路径，感兴趣可以看下。
