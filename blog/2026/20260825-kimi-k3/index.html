Kimi K3 技术报告解读 | 2.8T MoE 的架构与 Infra 细节：KDA、AttnRes、Stable LatentMoE 与 3T 级训练系统

原文：Kimi K3: Open Frontier Intelligence

1. 前言

开源 LLM 这两年在 post-training 上卷得很凶，但预训练底座的规模基本停在 1T 上下不动了。Kimi K3 是个例外：2.78T 总参数、104.2B 激活参数、1M token 上下文，比 K2 的 1.04T 直接翻了近三倍，官方给出的整体 scaling 效率提升约 2.5×。

但让我决定认真读一遍这份报告的原因不是分数，而是它把”怎么造出来的”写得异常完整：模型架构、3T 级预训练 infra、1M 上下文 agentic RL 系统、线上 serving，每一层都摊开讲了。这种全栈细节的 frontier 技术报告不多见，对做 infra 的人来说是很好的学习材料。

这篇文章我会重点讲两块：模型架构的细节（KDA、Attention Residuals、Stable LatentMoE）和基础设施的实现思路（训练、RL、推理），配简化代码和维度变化，让没做过 infra 的同学也能跟上。训练配方、评测结果这些就略过了。

2. 全局架构：三个维度上的信息流

K3 的架构设计可以概括为一句话：在序列长度、网络深度、模型宽度三个维度上，各自换掉默认的信息流动方式。

  • 序列维度：Hybrid Attention，每个 block 里 3 层 KDA（线性注意力）+ 1 层 Gated MLA（全局注意力），3:1 交替，backbone 末尾再补一层 MLA 保证最后一层做全局 attention
  • 深度维度：Attention Residuals（AttnRes），每层可以”回头”看前面所有层的输出，而不是只拿上一层的输出
  • 宽度维度：Stable LatentMoE，896 个 routed expert 每 token 激活 16 个，稀疏度 56×

3. KDA：用固定大小的状态换掉 KV Cache

3.1 先搞清楚问题：为什么需要线性注意力

标准 softmax attention 的问题是 KV cache 随序列长度线性增长：1M 上下文意味着每个 token 的 K、V 都得留着，推理时显存和访存都被它卡死。

线性注意力的思路是把历史信息压缩进一个固定大小的循环状态 S，新 token 来了只更新 S，不追加存储。KDA（Kimi Delta Attention）是这一类里的一个具体设计，核心是 delta rule：写入新信息的同时减掉旧信息里和当前 key 冲突的部分，相当于边写边擦，避免状态被无差别覆盖后饱和。

单头的循环形式（原论文 Eq.1）：

\[\mathbf{S}_t = (\mathbf{I} - \beta_t \bm{k}_t \bm{k}_t^\top)\operatorname{Diag}(\bm{\alpha}_t)\mathbf{S}_{t-1} + \beta_t \bm{k}_t \bm{v}_t^\top, \quad \tilde{\bm{o}}_t = \mathbf{S}_t^\top \bm{q}_t\]

用简化代码 + 维度走一遍（单个 head）：

# 伪代码：KDA 单头循环形式（简化辅助理解，非官方实现）
# x_t: [7168]  当前 token 的隐藏状态
# q_t, k_t: [d_k]   v_t: [d_v]   都是 x_t 过投影矩阵得到的
# S: [d_k, d_v]     循环状态，跨 token 持续更新，代替整个 KV cache

alpha_t = torch.exp(g_min * torch.sigmoid(e_A * z_t))  # [d_k]，逐通道遗忘因子 ∈ (e^-5, 1)
beta_t  = torch.sigmoid(W_beta @ x_t)                  # 标量，本次写入强度

# ① Diag(alpha_t) @ S：旧状态逐通道衰减（"遗忘"）
# ② (I - beta_t * k_t k_t^T) @ ...：减掉旧状态里与 k_t 同方向的部分（delta rule 的"擦除"）
# ③ + beta_t * k_t v_t^T：写入新内容
S = (torch.eye(d_k) - beta_t * torch.outer(k_t, k_t)) @ (alpha_t[:, None] * S) \
    + beta_t * torch.outer(k_t, v_t)

o_t = S.T @ q_t   # [d_v]，读状态得到输出，类似 attention 里 query 点积 K 再加权 V

和 RNN 的关键区别在于：这个循环虽然形式上串行，但可以重写成”chunk 间串行、chunk 内并行”的形式（原论文 Eq.4）——把序列切成长度 C 的 chunk，chunk 之间只传状态 S，chunk 内部的所有输出用矩阵乘法一次算出来：

# 伪代码：chunkwise 并行形式（简化）
# Q, K, V: [C, d_k / C, d_v]，当前 chunk 内所有 token 堆叠
# S_in: [d_k, d_v]，上一个 chunk 传进来的状态
Gamma = cumprod(alpha)                          # [C, d_k]，chunk 内累积衰减
A = tril((Q * Gamma) @ (K / Gamma).T)           # [C, C]，下三角因果 mask
V_tilde = U - W @ S_in                          # UT transform 得到的伪 value
O = (Gamma * Q) @ S_in + A @ V_tilde            # 前项跨 chunk，后项 chunk 内
S_out = ...                                     # 状态更新，传给下一个 chunk

这就是 KDA 能吃满 GPU Tensor Core 的原因：重活都是 dense matmul，串行的只有状态传递。

3.2 K3 的改动一：lower-bounded decay

chunkwise 形式里有个数值陷阱：公式里要对 key 除以累积衰减 Γ（相当于乘 1/Γ）。Γ 是一堆 (0,1) 区间数连乘，它的倒数可以任意大，低精度下直接 overflow。

Kimi Linear 的做法是 log 空间算相对衰减，且对角 tile（chunk 内自己乘自己的部分）只能逐位置对算，是性能瓶颈。K3 的改动非常简单：给 log-decay 加一个下界。原来用负 Softplus 映射，g 可以到 -∞；K3 换成缩放的 sigmoid：

\[\bm{g}_t^h = g_{\min} \cdot \operatorname{Sigmoid}(e^{A_h} \bm{z}_t^h) \in (g_{\min}, 0), \quad g_{\min} = -5\]

效果（如下图）：

  • 每步遗忘因子 α > e^(-5) ≈ 6.7×10⁻³，16-token tile 的累积 log-decay 落在 (-80, 0)，倒数最大不超过 e^80，BF16 动态范围内装得下
  • 于是对角 tile 也能用 dense Tensor Core matmul，逐位置对计算路径整个删掉，kernel 里不再有慢路径

一个很典型的”算法改一行，系统快一截”的例子。

3.3 K3 的改动二：full-rank output gate

Kimi Linear 里 KDA 的输出门是低秩投影，K3 换成输入相关的满秩投影：

\[\bm{y}_t = \mathbf{W}_o[\operatorname{Sigmoid}(\mathbf{W}_g\bm{x}_t) \odot \operatorname{RMSNorm}(\tilde{\bm{o}}_t)]\]

每个 token 自己决定状态读出来的哪些通道放行。Gated MLA 那边也做了同样的改动（把 RMSNorm 换掉，直接 gate 原始输出），两边的 gate 参数化保持一致。

3.4 Gated MLA 与 NoPE

MLA（Multi-head Latent Attention，DeepSeek-V2 提出）把每个 token 的 KV 压缩成一个低维 latent 向量 c_t，cache 里只存 c_t，attention 计算时再升维重建 K、V，用一点计算换 KV cache 体积。K3 在 3:1 的混合里保留 1/4 的 MLA 层做全局 attention。

两个细节值得注意：

  1. 所有 MLA 层用 NoPE（No Position Encoding），不加 RoPE。位置感知交给 KDA 层（衰减机制天然编码了”远近”），MLA 层只管内容交互。好处是长上下文扩展时完全不用动位置编码——不用重调 RoPE base，也不用 YaRN 插值，直接从 64K 扩到 1M
  2. 训练时 attention 输出保持 FP32（修正 flash attention 里一个有偏舍入误差），代价是片上输出 tile 翻倍，所以他们重写了训练 kernel，让输出 tile 和 KV staging buffer 共享 shared memory 而不是挤占 query tile

4. Attention Residuals：把 attention 从时间轴搬到深度轴

标准残差连接有个隐含假设：前面所有层的信息都无差别地累加进一个隐状态 h_l 传下去。层数一深，这就是深度轴上的 RNN 瓶颈——和当年序列轴上的 RNN 一模一样。

AttnRes 的解法也和当年一样：上 attention。每一层有一个可学习的伪 query w_l ∈ R^d，把前面所有层的输出当作 K/V，算一组数据相关的权重做加权求和：

# 伪代码：Full Attention Residuals（简化）
# H_prev: [l, d]，前面所有层的输出堆叠（第 0 行是 token embedding）
alpha = softmax(w_l @ RMSNorm(H_prev).T)   # [l]，本层对每层输出的关注度
h_l = alpha @ H_prev                        # [d]

对 K 做 RMSNorm 是为了防止某些层的输出幅值特别大、把 softmax 垄断掉。

问题在于显存：Full 版本要求所有层输出都活着，内存和 PP 跨卡通信都是 O(L·d)。所以 K3 实际用的是 Block 版本：93 层切成 8 个 block（每块 12 层），block 内部输出直接求和压缩成一个 block 表示 b_n，加上 embedding 一共 9 个 K/V。每层只从这 9 个表示里做加权检索，开销从 O(L·d) 降到 O(N·d)。论文说 N≈8 就能拿回 Full 版大部分收益。

5. Stable LatentMoE：896 选 16 的稳定化三件套

5.1 LatentMoE 的基本结构

MoE（Mixture-of-Experts，混合专家）的思路：FFN 不再是一个大矩阵，而是很多个小专家，router 给每个 token 挑几个，激活参数远小于总参数。K3 的配置是 896 个 routed expert 选 16 个，另有 2 个全宽 shared expert（所有 token 必经）。

K3 特有的设计是 latent 专家：routed 专家不在 7,168 维全宽空间里干活，而是在 3,584 维（0.5×）的 latent 空间里：

# 伪代码：Stable LatentMoE 前向（简化）
# x: [7168]，ℓ = 3584（latent 维度），专家中间层 3072

# ① router 打分 + Quantile Balancing 偏置（见 5.3），Top-16 选专家
scores = torch.sigmoid(W_r @ x)                       # [896]
idx, p = qb_topk(scores + b, k=16)                    # 16 个专家及其权重

# ② routed 分支：先降到 latent 空间
u = sum(p_i * E_i(W_down @ x) for i in idx)           # W_down: [7168→3584]，每个专家在 3584 维空间内计算

# ③ shared 分支：2 个全宽专家，所有 token 必经
y = W_up @ RMSNorm(u) + Shared_1(x) + Shared_2(x)     # W_up: [3584→7168]

为什么敢把专家砍到半宽？因为 shared 专家保住了全宽信息通路，routed 分支只负责”稀疏补充”。这样 896 个专家的参数量才压得住——如果专家都是全宽，896 选 16 的参数规模会失控。

5.2 稳定性：RMSNorm + SiTU-GLU

极端稀疏（896 选 16）放大了两个老问题：

  1. 激活爆炸。routed 路径是 W↓ → 专家 FFN → W↑ 四个矩阵乘连着来，本身病态；2.8T 规模下内部激活会爆
  2. 负载均衡难。近千个专家的均衡超出了 auxiliary-loss-free bias 更新能很好工作的范围

前一个问题用两招解决。一是在 W↑ 之前插 RMSNorm，把 u 的 scale 拉回来再升维。二是把 SwiGLU 换成 SiTU-GLU：

\[\text{SiTU-GLU}(x) = [\beta_1\tanh(\mathbf{W}_g x/\beta_1) \odot \sigma(\mathbf{W}_g x)] \odot [\beta_2\tanh(\mathbf{W}_u x/\beta_2)]\]
SwiGLU 的两个乘法分支都是无界的，激活值可以任意大，低精度训练里就是 overflow 隐患。SiTU-GLU 给两个分支各加了一个 softcap（β·tanh(x/β)，原点附近近似线性、大值处平滑封顶），**输出被硬约束在 f(x) ≤ β₁β₂ = 100 以内**（K3 取 β₁=4，β₂=25），同时原点附近的行为和 SwiGLU 几乎一样——不牺牲拟合能力：

5.3 Quantile Balancing：896 个专家的负载均衡

负载均衡这块，DeepSeek 系的做法是给每个专家维护一个 bias b_j，只加在 Top-k 选择上（不影响梯度），按负载情况 ±γ 地调。问题是指示器 sign 的更新粒度太粗，896 个专家时要么收敛慢要么负载震荡。

K3 的 Quantile Balancing（QB） 想法很漂亮：bias 不用慢慢试，一次前向就能直接算出来。步骤：

  1. 本 batch 用 Top-(k+1) 而不是 Top-k 路由：前 k 个是真实路由，第 k+1 名的分数就是”进入这个 token 的 Top-k 需要跨过的门槛” α_i
  2. 对专家 j，如果 bias 设成 b̂j，它会被多少 token 选中？就是满足 s{i,j} + b̂j > α_i 的 token 数。这个数随 b̂ 单调，令它等于目标负载 q = mk/n，解出来的 b̂ 就是”让专家 j 恰好达到目标负载”的 bias——数学上它就是 margin (s{i,j} - α_i) 的 (1-k/n) 分位数
# 伪代码：Quantile Balancing 更新（简化）
# s: [m, 896] router 分数，alpha: [m] 每个 token 的 Top-(k+1) 门槛
margin = alpha[:, None] - s                       # [m, 896]，专家进 Top-k 还差多少分
b_hat = -torch.quantile(margin, q=1 - k/n, dim=0) # [896]，逐专家取分位数
b = b_hat - b_hat.mean()                          # 去公共偏移（不影响 Top-k 结果）

工程上的关键：margin 是百万级、分散在各卡上的，直接 all-gather 不现实。K3 的做法是每个专家本地统计自己 margin 的直方图（1000 个 bin），all-reduce 直方图计数（整数加法，与数据怎么切无关），再从合并直方图里读分位数。通信量从”百万个浮点数”降到”每专家 1000 个整数”，误差只有 bin 宽度级别（10⁻³ 量级）。

6. 训练 Infra：3T 级 MoE 怎么跑起来

架构讲完了，进入 infra 部分。3T 参数、896 专家的预训练系统要解决三件事：专家并行负载不均、显存装不下、多模态编码器堵关键路径。

先补几个术语。TP/EP/PP/DP 分别是张量/专家/流水线/数据并行：TP 把单个矩阵切到多卡，EP 把不同专家放不同卡（卡间 all-to-all 搬 token），PP 把层切成流水线阶段，DP 复制整套模型跑不同数据。K3 的并行栈是 PP（带虚拟阶段）+ EP + ZeRO-1 DP + Pipeline ZeRO-2 梯度分片 + CP 的组合。

6.1 MoonEP：完美均衡的专家并行

EP 的经典痛点：router 是数据相关的，每个 batch 各专家收到的 token 数天然不均，最热的卡决定整体速度。ECHO 这类方案预设冗余专家数量或 token 上限，遇到极端分布可能直接中断训练，要人工调参。

K3 的 MoonEP（已开源）做到了数学意义上的完美均衡：每个 EP rank 恰好收到 S×K 个 token（S 序列长、K 每 token 选专家数），所有卡算一样的量。三个核心机制：

  1. 冗余专家迁移。热门专家复制一份到别的卡上分摊负载。理论保障：最多预留 E/R 个冗余专家槽位（E 专家数、R 并行度）就一定存在均衡方案，训练永远不会因找不到可行解而卡死
  2. 零拷贝通信。planning kernel 预先算好每个 token 的目的地，token 直接写到远端卡上按专家分组的位置，通信 buffer 直接以 view 形式交给计算。对比 DeepEP 的免拷贝路径需要按最坏情况开 S×K×R 的 buffer，MoonEP 只要固定 S×K
  3. 静态 shape 免同步。每层每卡 token 数恒等于 S×K，所有 kernel shape 编译期已知，host-device 同步和 host 侧 kernel launch 开销整个消失——这点对吃满 GPU 利用率非常关键

6.2 显存：一套组合拳

2.8T 模型的激活、梯度、优化器状态都远超单卡显存，K3 的做法是把”存哪里、要不要留”做成张量粒度的可组合策略：

  • 统一激活管理器：每个被保存的张量可以独立声明重计算/量化/offload/远端 offload 策略，与模型代码解耦。K3 实践里大部分激活用 block-wise FP8 量化 + offload，逐元素算子用重计算
  • MoE 反向省显存：把 permute 概率的梯度数学重写成只依赖中间激活和上游梯度，前向 group-GEMM 只存 dispatch 输入，反向时重算并和 GEMM 重叠
  • AttnRes 的显存优势：block 表示只在 block 边界层算一次、全层共享，整个 AttnRes 包进 checkpointing 后，每层保存的激活和标准残差架构一样多——深度轴上的 attention 几乎白拿
  • PP rank 间均衡：interleaved 1F1B 下靠前流水线阶段的激活驻留更多，用 Mooncake 传输引擎把激活 offload 到其他 PP rank 的内存里拉平
  • Pipeline ZeRO-2：梯度按 DP rank 分片后存 CPU 内存，GPU 上只留双缓冲
  • Muon 优化器的 P2P 正交化：Per-Head Muon 把 attention 投影矩阵按 head 切开分别做 Newton-Schulz 正交化（避免大梯度 head 垄断更新方向），但分片优化器下正交化需要完整矩阵。K3 不做全量 all-gather，而是每个 rank 只通过 P2P 拉自己拥有的参数的分片，通信和计算流水线重叠

6.3 KDA 的系统协同设计

KDA 的固定大小状态 S 既是算法优势（不用传 KV），也是系统难点（更新是串行的，不好切到多卡）。

  • FlashKDA kernel：chunkwise 计算里，chunk 内并行和跨 chunk 状态传递是交替的，naive 实现会在串行阶段让 SM 空转。FlashKDA（CUTLASS 实现）把两条路径拆成可独立调度的阶段做重叠，训练和 prefill 共用
  • 单卡内 CP：纯 TP 下超长序列 prefill 时每卡只分到几个 head，大量 SM 闲置。关键观察是每段的状态转移可以不依赖输入状态独立算，之后精确合并——于是在单卡 SM 层面做序列切分并行，零跨卡通信
  • 跨卡 KDA Context Parallelism：线性注意力的 CP 不能像普通 attention 那样各算各的再相加（KDA 的转移矩阵依赖输入状态）。KCP 把每段的效果拆成两个本地可算的量：累积转移矩阵 M（作用在入状态上）+ 从零状态算出的本地状态 S̃，一次 all-gather 交换这些固定大小的 fragment，再用前缀扫描恢复每个位置的入状态。通信量与序列长度无关，计算线性扩展

7. 1M 上下文 Agentic RL 的 Infra

K3 的 RL 是百万 token、成百上千次工具调用的长程任务，infra 要解决”状态活得久”的问题。

外部 KV cache 池（write-back 设计）：正在解码的 block 留在 GPU，空闲的可复用前缀在被驱逐时才写回 CPU DRAM，下次复用前预取。KDA 状态跟着对应的 MLA KV block 一起 offload/预取（两者生命周期一致）。训练迭代期间，模型权重和优化器状态进一步 offload 到 NVMe，把 DRAM 让给 cache 池。配合 partial rollout（长任务分段续跑），每个 1M 上下文的 RL 实验控制在几百张卡以内。

Rollout 自动节流：多步 rollout 中上下文越滚越长，固定并发要么喂不饱要么打爆引擎。调度器根据活跃请求数、排队数、KV cache 利用率动态调节发给推理引擎的请求量。

梯度 buffer 复用：reference model 太大放不进显存，权重常驻 CPU、按需搬入。搬进哪里？直接复用 policy 模型的 FP32 梯度 buffer——ZeRO-2 分片下每卡只有两个 VPP chunk 的梯度 buffer，reference 权重逐 chunk 流水线式进出：一个 chunk 在算，另一个在预取。

沙箱（AgentENV，已开源）：agent 会挂载磁盘、起容器、跑内核操作，普通容器隔离不住（真的会内核 panic）。K3 用 Firecracker microVM，几个数字感受一下：

  • 增量 checkpoint 只存脏页，checkpoint 133ms、resume 49ms——agent 等推理结果时沙箱可以整个暂停（这类等待占沙箱生命周期最高 98%），不占任何内存 CPU
  • Fork 可以克隆出状态完全一致的沙箱且原沙箱继续跑，无副作用的 reward 评判就靠这个
  • OverlayBD 镜像 + P2P 传输，秒级拉起数万个沙箱，内存超卖比到 6.5×
  • 整个 K3 训练+评测累计创建了 5120 万+ 个沙箱

8. 线上 Serving：KDA 时代的 Prefix Cache

推理侧最有意思的是 KDA 让 prefix cache 的设计变复杂了。传统 KV cache 按 token 分页，任意前缀边界都能复用；KDA 的状态是每请求一份的固定大小张量，只有存了 checkpoint 的边界才能恢复。两种缓存的大小、生命周期完全不同，但一个请求的前缀要么都能复用、要么都不能。

K3 的解法是统一 cache 布局 + 粗细两级粒度解耦：

  • KDA 状态打包进和 MLA KV 同样的分页 block 池，page 统一字节大小，分配/引用计数/驱逐一套代码全搞定
  • 前缀哈希在 512-token 的 hash block 粒度上做，物理 block 仍是粗粒度分配单位（比如一个 6144-token 物理块 = 12 个 hash block）。KDA checkpoint 只在稀疏的 hash 边界存（通常是轮次边界）
  • 命中时：MLA 部分按链式哈希匹配到任意 hash 边界，KDA 部分恢复最近的 checkpoint，未命中部分 copy-on-write 后继续 prefill

效果是任意共享前缀在任意 512-token 边界都可复用，与请求长度、chunking 方式、调度交错无关。

decode 侧，KDA + MTP speculative decoding 组合有个麻烦：draft token 被拒后状态已经往前走了，逐位置存状态快照的通信开销在大 batch 下是主导成本。K3 的 kernel 只缓存 draft token 的投影输入（比状态小得多），被接受的 token 状态在片上重放重建，再把验证后状态写回——单 fused kernel 覆盖短卷积、归一化、门控、KDA 循环全流程。

集群调度层面还有两个实用设计：典型 coding 请求是 400K token 前缀 + 4K token 增量，cache 命中比 miss 便宜几个数量级，所以请求要路由回持有它前缀的集群（每 session 绑主备两个集群，故障时备用集群重新 prefill）；长短请求成本差三个数量级（<2K 到 1M），按请求类别分配独立资源预算，防止长上下文流量挤爆全系统 TTFT。

另外部署侧的量化也值得一提：post-training 全程（SFT + RL）做 MXFP4 量化感知训练——MoE 专家权重 MXFP4、激活 MXFP8，attention 投影、router 等非专家部分保持高精度，rollout 和训练用同一套量化消除 train-inference mismatch。

9. 结语

整份报告读下来，最大的感受是架构改动和系统实现是咬合在一起的：lower-bounded decay 换来全 Tensor Core 的 kernel；AttnRes 的 block 结构让训练显存和 serving kernel 都有对应的简化设计；KDA 的固定状态既是长上下文的算法优势，又催生了全新的 cache 管理系统；连激活函数换成 SiTU-GLU 都有低精度量化的考量。单独看每一处都是”小改动”，拼起来就是 2.5× 的 scaling 效率。

对想做 infra 的同学，我的建议是按 5.2（MoonEP + 显存管理）→ 5.4（prefix cache）→ 5.1（KDA kernel）的顺序读，第一块是所有大模型训练系统的通用功，后两块则是 KDA 这种新架构带来的全新问题，比较有前瞻性。

顺带一提，MoE 稀疏化、量化（MXFP4 这类低精度格式）本质上都属于 LLM 压缩这个大方向，我们之前把这个方向的方法论积累整理成了一本《动手学 AutoML：从 NAS 到大语言模型优化实战》，里面有 LLM 压缩（剪枝、量化）和后训练剪枝实战的章节。K3 这篇报告讲的是训练/推理系统层面的优化，和书里的压缩视角是同一目标下的不同角度，感兴趣可以搭配着看。
